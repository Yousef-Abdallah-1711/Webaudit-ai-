## Network, Ref and Identity

- [x] CHK-SA001 Is acquisition network I/O confined to the existing SSRF-guarded fetch with a fixed host allowlist
  (`api.github.com`, `codeload.github.com`), with an out-of-allowlist redirect required to abort? [Completeness, Spec
  §FR-005; source-acquisition-contract invariant 2]
- [x] CHK-SA002 Are the input grammars for `repositoryFullName`, `requestedRef` and `workspacePath` specified so a
  crafted value cannot alter the request path, query or host? [Clarity, Spec §FR-001, §FR-002;
  source-acquisition-contract §Inputs]
  **RESOLVED (pass 3)**: FR-151 and source-acquisition-contract Inputs 5 define grammars for `repositoryFullName` (incl. `.`/`..`/`.git`), `requestedRef` (percent-encoded as one path segment; `?`, `#`, `%`, backslash rejected), SHA, and `workspacePath`; content is fetched only by the resolved SHA.
- [x] CHK-SA003 Is the git protocol and git binary absence stated as an absolute prohibition (no clone, no hooks, no
  repository-supplied program, in any trusted process or build)? [Completeness, Spec §FR-005;
  source-acquisition-contract boundary rule 3]
- [x] CHK-SA004 Does the requirement close the branch-moves-between-resolve-and-fetch race by resolving to a 40-hex SHA
  first, fetching by SHA, recording both refs, and reusing the recorded SHA on retry? [Consistency, Spec §FR-002,
  §User Story 1 scenario 1; source-acquisition-contract §Idempotency 3]
- [x] CHK-SA005 Is the F01 decision on the requested ref recorded together with the resolved SHA, with the SHA as the
  sole executed identity and a SHA-only grant refusing a branch-name request (`OUT_OF_SCOPE`)? [Clarity, Spec §FR-004,
  §Clarifications; source-acquisition-contract §Safety 3]
- [x] CHK-SA006 Is the timing of the workspace-path scope check stated once? [Consistency, Spec §FR-004;
  source-acquisition-contract §Failure behavior; research R1]
  **RESOLVED (pass 3)**: The scope check timing is stated once (after ref resolution, before any content fetch): acquisition contract invariant 10; research R1 aligned.
- [x] CHK-SA007 Are GitHub API failure modes beyond revoked/missing and 5xx classified (rate limit or abuse 403/429,
  archived or empty repository, private repository where the token lost access mid-scan, oversized zipball)?
  [Edge Case, Spec §FR-012; source-acquisition-contract §Failure behavior]
  **RESOLVED (pass 3)**: Acquisition failure table classifies GitHub rate limit (`TRANSIENT_INFRASTRUCTURE`), archived/forbidden (`TARGET_UNAVAILABLE`) and oversize (`SOURCE_TOO_LARGE`).
