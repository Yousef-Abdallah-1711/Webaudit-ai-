# Contract: Execution Fixtures

Per FR-082 through FR-084, FR-096, FR-097, FR-100 and FR-106 (with FR-083, FR-098, FR-105, FR-107). Fixtures shared by
backend and database testing: ephemeral, in-Guest service doubles and the disposable PostgreSQL. A fixture is not a
Target (no 007 change). Consumers: untrusted-execution-contract, command-policy (`db.*`, `backend.start.recognized`,
`test.*`), Backend, Database and Automated Tests Source Checks, source-evidence-contract.

## Signature (shape, not final TypeScript)

```text
FixtureSpec = { fixtureSpecId, version, fixtures: FixtureRef[], seed: int, env: Record<name, FixtureBinding> }
FixtureRef = { kind: POSTGRES16 | MAIL_SINK | HTTP_STUB | FAKE_PAYMENT_GATEWAY | QUEUE, instanceId, imageProvides: true,
  limits{memMiB,diskMiB,connections,rowsPerTable (default and cap 1,000),wallMs}, startTemplateId, healthCheck{kind,timeoutMs,retries},
  resetStrategy: NONE | TRUNCATE_RESEED | RESTORE_TEMPLATE, cleanup: WITH_GUEST }
FixtureBinding = { var: "DATABASE_URL"|"SMTP_URL"|"PAYMENT_BASE_URL"|..., value: fixture-derived (loopback/socket only) }
selectFixtures(detectionEvidence, suiteClassification, requestedFixtureSpec) -> FixtureSpec | UNMET(requirement[])
fixtureLifecycle: SELECTED -> STARTING -> HEALTHY -> IN_USE -> RESET* -> DESTROYED(with Guest)
```

## Inputs

Static discovery results (env var reads, route inventory, test classification), the explicit `FixtureSpec` chosen from
what the Execution Image provides, migration/seed files from the snapshot (as data), deterministic seed.

## Outputs

`EXECUTION_STEP_RESULT` for each fixture start/health/reset; `SCHEMA_SNAPSHOT`/`MIGRATION_RESULT` evidence produced
against the PostgreSQL fixture; fixture identity (kind, instanceId, version, image digest, seed) recorded in every
dependent `TEST_RESULT`/`CONTRACT_RESULT`; `NON_DISPOSABLE_DATABASE_REFERENCE` flags (path and variable name only; a FLAG annotation, never a verdict by itself).

## Ownership

The Supervisor selects and sequences fixtures; templates (`db.postgres.start`, doubles' start templates) are platform
code; the Guest runs them. Customer source supplies only migrations, schema, tests and static env-var names.

## Invariants

1. Allowed fixtures only: in-Guest PostgreSQL 16 (unix socket/loopback, data dir on guest tmpfs), mail sink, generic HTTP
   stub, fake payment gateway, and a queue fixture (Redis-compatible, in-Guest) only where the signed image provides one (FR-097).
2. Selection is explicit: a fixture starts only if named in the `FixtureSpec`; no auto-attach based on detected env
   names, and no wiring other than variables the platform sets. Needing an unmapped service means `REQUIRES_EXTERNAL_SERVICE` (FR-082).
3. Properties (FR-083): ephemeral (destroyed with the Guest), bounded (limits above; 1 PostgreSQL instance per run),
   tenant-isolated (one Guest per run, FR-046), reproducible (seeded PRNG, FK-ordered bounded rows, fixed TZ/locale).
4. Startup, health, reset: start via recognized template, then health check (Postgres `pg_isready` plus a `SELECT 1`;
   doubles: readiness endpoint) within `timeoutMs` (default 60 s) before any dependent Step; `resetStrategy` is applied
   between test groups. A reset strategy never makes an integration Step rerunnable: reruns (FR-086) apply only to unit-test Steps that start no fixture (`rerunSafe`); ALL integration Steps, even with a resettable fixture, are never rerun in v1. Reset exists only to give the next group a clean state.
5. Synthetic env (FR-096): every required variable is discovered statically (`process.env.X`) and bound to either a
   fixture value or a synthetic non-secret placeholder (`FAHES_SYNTHETIC_<NAME>` shape); `DATABASE_URL` and aliases
   (`POSTGRES_URL`, `DIRECT_URL`, `SHADOW_DATABASE_URL`, `*_DB_URL`) point only at the in-Guest instance.
6. Never real production services, never copied production data (FR-083); customer-provided connection strings are never
   used to connect (FR-100). Values found in source or environment that look non-disposable (host not loopback/socket,
   managed-DB hostname patterns, credential-bearing URI) are ignored, never echoed, and recorded as
   the FLAG `NON_DISPOSABLE_DATABASE_REFERENCE` (an observation; never used to connect; DB checks proceed on the in-Guest fixture) with file path and variable name only.
7. Migrations and destructive operations execute only against the disposable instance; they never mutate real records
   (FR-106); destruction inside the fixture is permitted (provisional product default).
8. Test-data lifecycle: seed data is generated by Fahes from the parsed schema (deterministic seed, bounded rows <= 1,000
   per table, FK-ordered, constraint-aware; produced by the in-Guest tool `db.seed.synthetic`), never from customer data; teardown is Guest destruction, never partial cleanup
   trusted as proof; evidence stores no row contents beyond bounded synthetic samples (FR-109).
9. Egress stays none after P3; doubles are loopback-only; fake gateways never forward traffic.
10. Kill or timeout mid-migration destroys the Guest and its database; evidence states a stopped execution and never a
    partially applied state as a completed migration (FR-107).
11. Fixture failures never count as customer test failures (FR-084).

## Failure behavior

| Condition | Reason code | FailureClass | Verdict |
|-----------|-------------|--------------|---------|
| Fixture fails to start or health check | `FIXTURE_STARTUP_FAILED` | none | dependent Steps `BLOCKED`; suite status `RUNNER_SETUP_FAILED` |
| Fixture start exceeds its limit | `FIXTURE_STARTUP_FAILED` (the start Step result is `TIMED_OUT`) | none (measured) | `BLOCKED` |
| Fixture exceeds memory/disk/connections | `RESOURCE_LIMIT_EXCEEDED` | none (measured) | `INCONCLUSIVE` |
| Required fixture not offered by image | `REQUIRES_EXTERNAL_SERVICE` | none | `NOT_TESTED` |
| PostgreSQL major or dialect other than 16 | `UNSUPPORTED_VERSION` | none | `UNSUPPORTED` |
| Non-disposable DB reference in source/env | `NON_DISPOSABLE_DATABASE_REFERENCE` (FLAG) | none | observation only, no verdict of its own; never used to connect; execution and DB checks continue on the in-Guest DB |
| Test attempted outbound call (blocked) | `NETWORK_BLOCKED_BY_POLICY` | none | annotated; coverage `REQUIRES_EXTERNAL_SERVICE` |
| Missing synthesizable env | `MISSING_ENV_VAR` | none | `NOT_TESTED` |
| Seed cannot be generated from the schema (unsupported column type) | `FIXTURE_GENERATION_UNSUPPORTED` | none | `NOT_TESTED` (that table) |
| Run envelope exhausted before the fixture starts | `RUN_BUDGET_EXHAUSTED` | none | `INCONCLUSIVE` |

A fixture breach of containment (Guest agent tamper) is recorded as the flag `SANDBOX_POLICY_VIOLATION` and aborts with `CONTAINMENT_ABORT`: `CUSTOMER_CODE_FAILURE`, unit `FAILED`, checks `BLOCKED`.

## Safety

Fixtures hold no real credentials; synthetic passwords are generated per run and never persisted. Fixture ports bind
loopback or unix sockets only. Fixture logs pass `@webaudit/redaction` and byte caps before leaving the Supervisor.

## Idempotency

`FixtureSpec` and seed are deterministic from `(snapshotDigest, specId, version)`; fixture start steps carry keys
`H(executionUnitId, attempt, stepIndex)`; a repeated start inside the same Guest is a no-op only if the health check already passes.

## Consumers

Backend, Database and Automated Tests Source Checks; execution-fixture evidence rows in `TEST_RESULT`, `MIGRATION_RESULT`,
`CONTRACT_RESULT`; reverify planner (migration test only).

## Non-negotiable boundary rules

1. No connection from a Guest to any non-Guest database, service or customer endpoint, ever.
2. No production data, credential or connection string is read into a fixture or echoed in evidence.
3. Fixture setup failure is never presented as a customer test failure or as PASS.
4. A fixture not named in the `FixtureSpec` does not start.
5. Fixtures do not become Targets, and live API/database targets belong to SPEC 012/013, not here.
