### Session 2026-10-10 (planning pass; repository evidence + frozen upstream + conservative defaults; items marked **PRODUCT DECISION — PROVISIONAL** carry the safest default and are NOT approved until the owner confirms them; items marked **OWNER-APPROVED 2026-10-11** (P1, P2, P3, P7, P10/AR-3, P13, P15) were explicitly approved by the project owner, and P11 is explicitly DEFERRED to credential-broker activation; no approval is inferred for any other decision — see plan.md §"Product decisions")

- Q: Which execution classes carry 012 work, and do we need a new class? → A: **No new class.** Authenticated sessions and cross-identity workflows run as `AUTHENTICATED_WORKFLOW` units (engine E15); crafted, adversarial or mutating probes run as `ACTIVE_SECURITY` units (engine E14); passive observations are parent-side registry checks over `PASSIVE_HTTP` / `BROWSER` / `CRAWLER` / `SOURCE_STATIC` evidence; API-surface inventory and advisory matching are parent-side deterministic derivations with no network. Queues are the 009 queues `webaudit-exec-active-security` and `webaudit-exec-authenticated-workflow`. (006 decisions.md l.160 open question "one engine invoking the other vs a composite class" → resolved as **no composite class**: a composite test generates one unit per class linked by an `ExecutionDependency` edge, per 009 `execution-unit-contract`, and 007 FR-006 independent per-class checks.)
- Q: Can any active-security class run against PRODUCTION? → A: **No.** 007 FR-015a forbids `PRODUCTION` in the grant of `ACTIVE_SECURITY` / `AUTHENTICATED_WORKFLOW` unconditionally. 012 requests **no** amendment. Any check whose probe definition computes to an active or authenticated class is refused at plan resolution and again at dispatch against a PRODUCTION or unclassified target (`SEC_PRODUCTION_PROHIBITED` / `SEC_ENVIRONMENT_UNCLASSIFIED`). Only passive observations (no crafted request, no credential) run in production.
- Q: Does F01's `isAuthorized` enforce `includedAccountRefs` / `includedRoles` / `includedActionCategories`? → A: **No** — 007 defines their *shape* and defers their semantics to F05 (this spec) and gives `isAuthorized` no account/role/action parameter. 012 therefore defines the semantics (account ref = `TestIdentity.id`, role = `TestRole.key`, action category = the closed list in security-scope-contract) and enforces them in its own `securityScopeGate`, **in addition to** F01 and F07, fail closed. This is a *named limitation*: enforcement is by 012 code plus conformance tests, not by F01 (same governance model as 008 FR-019). An optional upstream amendment AR-1 (give `isAuthorized` an action-category/account argument) is recorded in `upstream-amendment-requests.md` as a hardening candidate, **not required** for the architecture to be safe.
- Q: Is a new Target kind needed for APIs? → A: **No.** An HTTP API is a `WEB`-kind destination (host/path/scheme/port); its host MUST already satisfy 007's boundedness rule (the Target's own canonical host or a subdomain). An API on a different registrable domain needs its own verified Target and its own grant; grants are never combined (007 FR-013), so cross-domain composite flows are `UNSUPPORTED` in v1. Live *database* targets are out of scope entirely. **P10 / AR-3 — OWNER-APPROVED 2026-10-11**: an existing web target may cover APIs when F01 authorization and scope requirements are satisfied for the API destination (host/path/scheme/port within the grant's scope and boundedness rule); there is no distinct API Target kind, so 011's remark about a 007 amendment does not apply and **no upstream amendment is required** for this decision.
- Q: Are customer-provided test accounts mandatory? → A: **PRODUCT DECISION P1 — OWNER-APPROVED 2026-10-11: Yes.** Fahes never creates, guesses, harvests or brute-forces credentials. Any authenticated, authorization or business-logic check requires customer-registered `TestIdentity` records bound to a `TestRole`, at least one pair of identities for horizontal tests, and customer-controlled fixture resources.
- Q: Are state-changing (mutating) security tests supported? → A: **PRODUCT DECISION P2 — OWNER-APPROVED 2026-10-11: supported only on non-production targets, only against customer-registered `FixtureResource` records, and default OFF** (each mutation class is individually enabled per grant-scoped consent). Everything else is non-mutating. Real payments, refunds, purchases, emails/SMS to real recipients and inventory changes are never performed (FR-117, FR-119).
- Q: Is MFA supported? → A: **PRODUCT DECISION P3 — OWNER-APPROVED 2026-10-11**: v1 supports only (a) customer test identities for which MFA is disabled/exempt in the test environment and (b) a customer-provided pre-established test session fixture with a declared expiry. TOTP-seed storage, SMS/email OTP interception and human-assisted checkpoints are deferred (`SEC_MFA_CHALLENGE_UNSUPPORTED`). Fahes never claims or attempts an MFA bypass.
- Q: Is dependency-advisory matching in v1? → A: **PRODUCT DECISION P4 — PROVISIONAL (not yet approved): Yes, offline only**: matching of 011 `DEPENDENCY` facts against a versioned, provenance-stamped `AdvisorySnapshot` (OSV-format import) with a freshness bound. No live advisory lookup during a scan, ever. The 7-entry `dependency-scanner` table is REPLACED for advisory claims (its manifest/lockfile-hygiene checks are REUSED).
- Q: Can customers define business-logic invariants? → A: **PRODUCT DECISION P5 — PROVISIONAL (not yet approved): Yes, as declarative data, not code** — a closed predicate vocabulary evaluated deterministically over recorded observations. No customer-supplied scripts are ever executed. No invariant ⇒ no business-logic verdict.
- Q: Which API description types are supported? → A: **PRODUCT DECISION P6 — PROVISIONAL (not yet approved)**: OpenAPI 3.0 / 3.1 (JSON or YAML, bundled, no external `$ref`), plus 011 `SOURCE_SURFACE` routes and observed authorized traffic (`HTTP_TRANSACTION`). GraphQL, gRPC, SOAP and WebSocket APIs are `SEC_UNSUPPORTED_TARGET_TYPE`.
- Q: Is authenticated browser-based testing (DOM XSS in an authenticated page) supported? → A: **No in v1.** 010 gives every `BROWSER` unit a fresh zero-state context and defines no session-injection primitive; adding one is an upstream amendment (AR-2) that this spec does not need for HTTP-level authenticated testing. Browser-based checks in v1 are unauthenticated, run only through 010's `BROWSER` units, and are non-mutating.
- Q: Private-network / on-prem staging targets? → A: **Unsupported in v1.** `safe-net` cannot dial private space and this spec will not weaken it (FR-079). A customer-hosted agent is a future spec.
- Q: ModuleType and pricing? → A: **Reuse `SECURITY`; no new `ModuleType` value, no change to `AREA_COST`.** API / Auth / Authorization / Business-Logic are coverage *facets* inside the SECURITY module result, not new modules. **P15 — OWNER-APPROVED 2026-10-11 (partial billing)**: a customer is charged only for billable work actually executed; checks that end `BLOCKED`, `NOT_TESTED`, `UNSUPPORTED` or refused are never billed (FR-189); pricing per component and the refund rule are F06 dependencies (AR-15). **P13 — OWNER-APPROVED 2026-10-11**: uncapped `DEGRADED` scoring is rejected as a readiness PASS; observed evidence-backed scores are preserved; a positive production-readiness verdict is prohibited while required security coverage is incomplete (FR-188). **P7 — OWNER-APPROVED 2026-10-11**: passive-first release; authenticated testing only behind the activation gates. **P11**: KMS provider selection is DEFERRED and must be resolved before credential-broker activation (SG3).
- Q: Does a credential revocation mid-run need an F07 kill-switch reason? → A: **No upstream change.** 008's `KillSwitchReason` and `ExecutionAuditEventType` are closed. 012 maps broker-side revocation to its own *local* stop (the engine re-validates the credential lease at every checkpoint and ends the unit `COMPLETED` with verdict `BLOCKED` / `SEC_CREDENTIAL_REVOKED`, or `FAILED` per 009 classification), and records detail in the existing `AuditLogEntry` and in the redacted `payload` of existing `ExecutionAuditEventType` values — never a new enum value.
- Q: How are byte/auth-attempt/mutation budgets enforced given F07 ledgers only requests and concurrency? → A: F07 stays authoritative for **requests, concurrency, duration (via grant expiry)**. Bytes, auth attempts, per-endpoint, per-identity, redirect depth, retries and mutation counts are **engine-local limits, pre-checked before each request and labeled "locally enforced, not F07-ledgered"** in every contract and report. They may only be *tighter* than F07's, never a substitute. A true F07 byte dimension is optional amendment AR-4.

- Q: May active testing proceed against a destination whose origin cannot be shown to belong to the customer (shared edge, CDN, PaaS, tenant-controlled reverse proxy or forwarder)? → A: **PRODUCT DECISION P16 — PENDING owner approval; fail-closed default = refused for every destination.** Technical proofs (FR-172) establish control of the serving front only; a tenant-controlled forwarder to a third party's origin is undetectable (FR-197). Active/authenticated testing requires the Destination Authorization Policy: verified address binding, an origin-ownership warranty, an operator-reviewed `ActiveTestingEnablement`, and containment controls. Customer attestation alone is never treated as proof.
- Q: How is partial security work billed? → A: **P15 OWNER-APPROVED as a principle only** (charge only for executed billable work); its implementation is **not approved**. **Conservative default (`AREA_COUNT`)**: today's billing and refund semantics are unchanged (FR-189); active/authenticated work is not purchasable. **P17 PROPOSED, NOT approved**: execution-class-level billing with execution-backed partial settlement (FR-198), usable only if the owner approves P17 and the ADR-005 amendment AR-17; the passive partial-coverage billing gap is stated openly in FR-189.
- Q: Are private-CA or self-signed staging certificates, plain-HTTP targets or non-default ports supported for active testing? → A: **P18 PENDING (default unsupported in v1 for all three)**: certificate validation is never relaxed; plain-HTTP targets and non-default ports are refused (`SEC_UNSUPPORTED_TARGET_TYPE`); a customer-pinned certificate option would need its own reviewed policy.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Passive security configuration observations with honest coverage (Priority: P1)

A customer scans a verified production site. Fahes evaluates security headers, cookies, TLS-visible facts, CORS-visible response headers, CSP, caching and disclosure from responses the platform already fetched passively, using versioned deterministic checks that parse values (not just presence), and reports each check as a finding, an informational observation, or an explicit "not tested / unsupported" — never as a blanket PASS.

**Why this priority**: it is the only slice that is allowed in production, needs no credentials, and establishes the registry, evidence, finding and coverage foundations everything else depends on.

**Independent Test**: with only Contexts A, D and J wired and the active engines off, scan fixture responses (weak CSP, missing HSTS, cookie without flags, permissive CORS, debug banner, strong config). Verify per-check verdicts, CWE/OWASP tags, that a strong configuration yields `NO_ISSUE_DETECTED` scoped to "executed checks", that a target on which no response was captured yields `NOT_TESTED` (not PASS), and that no crafted request was sent.

**Acceptance Scenarios**:
1. **Given** a PRODUCTION target with only a verified domain and no active-security grant, **When** a security scan runs, **Then** only passive checks execute, every active/authenticated check is recorded `BLOCKED` with `SEC_PRODUCTION_PROHIBITED` (the environment filter runs **before** the F01 call; the F01 reason `NO_MATCHING_GRANT` is what a non-production target without a grant yields), and the SECURITY module result is `DEGRADED`, not complete.
2. **Given** a response with `Content-Security-Policy: default-src * 'unsafe-inline'`, **When** `sec.cfg.csp-weak` evaluates, **Then** a `CONFIGURATION_RISK` finding is materialized with severity ≤ MEDIUM and no exploitability claim.
3. **Given** zero responses captured, **When** the sweep runs, **Then** every passive check is `NOT_TESTED` with `SEC_NO_EVIDENCE` and the area score is `null`, never 100.

### User Story 2 — Customer-controlled credentials and short-lived scoped sessions (Priority: P1)

A customer registers a test identity (username/password, API key or bearer token, pre-established session fixture) for a non-production environment. Fahes stores it under envelope encryption, never shows it again, delivers it only to a trusted execution context for the duration of one execution unit, isolates every session per unit/identity/tenant, and destroys it on every exit path (complete, fail, cancel, kill, crash, grant expiry).

**Why this priority**: F05 is the security boundary for all authenticated testing; a leak here is a customer-data incident.

**Independent Test**: with fake KMS and fake broker, verify: no raw secret in ScanPlan, ExecutionUnit, queue payload, log, Evidence, Finding, AI prompt or report; broker refuses cross-tenant, cross-target, expired, revoked and wrong-unit requests; a session cannot outlive its grant; cleanup runs on kill and crash recovery.

**Acceptance Scenarios**:
1. **Given** a registered credential, **When** a unit is dispatched, **Then** the queue payload is exactly `{executionUnitId}`, the unit carries only `credentialBindingRef`, and the secret reaches the child process only over parent IPC after the broker re-validates unit state, lease, grant, tenant, target and identity.
2. **Given** a grant that expires mid-run, **When** the next checkpoint runs, **Then** the session is invalidated locally, the broker lease is revoked, and the unit ends without a PASS.
3. **Given** a credential rotated during a scan, **When** a unit starts, **Then** it pins the `CredentialVersion` resolved at its start and records that version id (never the value) in Evidence.

### User Story 3 — Authentication workflow observations (Priority: P2)

On a non-production target with a granted `AUTHENTICATED_WORKFLOW` class, Fahes runs bounded login, session, logout and recovery-structure checks with explicit expected outcomes and never guesses passwords.

**Independent Test**: fixture auth server; verify session creation, cookie flags, invalidation after logout (re-use of the old token is rejected), expired-session handling, fixation indicator (session id unchanged across login), account-lockout risk gating, and that `SEC_CREDENTIAL_REJECTED` is `BLOCKED`, never PASS.

**Acceptance Scenarios**:
1. **Given** a bad password supplied as the registered identity's credential, **When** login fails, **Then** the check is `BLOCKED` (`SEC_CREDENTIAL_REJECTED`), exactly one attempt was made, and no retry occurred.
2. **Given** a logout followed by reuse of the pre-logout token, **When** the protected endpoint still returns 200, **Then** `auth.session.logout-invalidation` records a `LIKELY_VULNERABILITY` (evidence: two transactions) or `CONFIRMED_VULNERABILITY` only if the fixture's oracle confirms the same resource.

### User Story 4 — Authorization boundary testing with synthetic fixtures (Priority: P2)

With two or more customer test identities in different roles/tenants and customer-owned fixture resources, Fahes compares expected permissions (a customer-declared `AuthorizationExpectation` matrix) against observed responses and reports confirmed failures separately from suspected weaknesses and fixture limitations.

**Independent Test**: fixture API with a deliberate BOLA and a deliberate BFLA; verify pairwise comparison, `CONFIRMED_VULNERABILITY` only where the expectation matrix and a differential oracle agree, `INCONCLUSIVE` with `SEC_FIXTURE_LIMITATION` when only one identity exists, and that no resource outside the registered fixtures is ever requested.

**Acceptance Scenarios**:
1. **Given** two registered identities in different roles and a customer fixture owned by identity A, **When** identity B requests it and the response contains A's fixture marker while the expectation says `DENY`, **Then** the pair is `CONFIRMED_VULNERABILITY` only if the actor's negative-control read lacks the marker, otherwise `LIKELY_VULNERABILITY`.
2. **Given** only one registered identity, **When** an authorization check is planned, **Then** it is `INCONCLUSIVE` with `SEC_FIXTURE_LIMITATION` and no request is made for the missing pair.
3. **Given** a probe that would use an identifier not in `FixtureResource.identifiers`, **When** the engine builds the request, **Then** it is refused (`SEC_FIXTURE_INVALID`) and never sent.

### User Story 5 — API discovery separated from API probing (Priority: P2)

Fahes builds an `API_SURFACE` inventory from OpenAPI, 011 `SOURCE_SURFACE`, and observed authorized traffic without any network access, then tests only endpoints that are both discovered **and** authorized in scope, with bounded schema-aware probes.

**Independent Test**: spec with 40 operations, 12 in scope; verify inventory = 40, authorized = 12, tested ≤ 12, skipped 28 with reasons, external `$ref` refused (`SEC_API_SPEC_EXTERNAL_REF_REFUSED`) with no network call, and that discovery alone never causes a request.

**Acceptance Scenarios**:
1. **Given** an OpenAPI document with an external `$ref`, **When** the inventory is built, **Then** the reference is refused (`SEC_API_SPEC_EXTERNAL_REF_REFUSED`) with no network call.
2. **Given** an operation that is discovered but not covered by the grant's class or scope, **When** probes are planned, **Then** it is recorded `SEC_API_NOT_AUTHORIZED` and no probe is sent.
3. **Given** an undeclared operation (no `ApiOperationDeclaration`, FR-192), **When** active probes are planned, **Then** it receives none (`SEC_MUTATION_NOT_PERMITTED`) regardless of HTTP method, while static checks still run.

### User Story 6 — Bounded injection / XSS / CSRF indicators without exploitation (Priority: P3)

Fahes detects input-validation and CSRF/XSS *indicators* with harmless, bounded, canary-style inputs on non-production targets, labels weak signals as such, and never extracts data or executes commands.

**Independent Test**: fixtures with (a) reflected-unescaped canary, (b) escaped canary, (c) SQL-error banner, (d) benign error page that mimics one. Verify (a) `LIKELY_VULNERABILITY`, (b) `NO_ISSUE_DETECTED`, (c) `LIKELY` not `CONFIRMED`, (d) `INCONCLUSIVE` (`SEC_SIGNAL_WEAK`); and that no payload exceeds the registry's declared harmless alphabet.

**Acceptance Scenarios**:
1. **Given** a reflected unescaped canary in an executable context, **When** the check evaluates, **Then** the verdict is `LIKELY_VULNERABILITY`, never `CONFIRMED`, with a `confirmationLimitation`.
2. **Given** a generic HTTP 500 in response to a canary, **When** the check evaluates, **Then** the verdict is `INCONCLUSIVE` (`SEC_SIGNAL_WEAK`) and no Finding is materialized.
3. **Given** a missing CSRF token, **When** the check evaluates, **Then** it is at most `CONFIGURATION_RISK`/`INFORMATIONAL`, never reported as exploitable.

### User Story 7 — Business-logic invariants and mutation cleanup (Priority: P3)

A customer declares invariants for a non-production fixture workflow (e.g. "a discount code is single-use", "order total equals sum of line items"). Fahes executes the bounded workflow, evaluates invariants, cleans up fixture mutations, and refuses to report PASS if cleanup failed.

**Independent Test**: fixture shop; verify duplicate-mutation suppression after a worker retry (`attempts: 1`, write-ahead intent), cleanup failure ⇒ `INCONCLUSIVE` + `SEC_CLEANUP_FAILED` + residual manifest, no request after a kill-switch stop (including cleanup), and no real-payment endpoint is reachable.

**Acceptance Scenarios**:
1. **Given** a fixture workflow with a declared invariant `AT_MOST_ONCE(discount)`, **When** a bounded repeat applies the discount twice and the invariant evaluates `false`, **Then** the verdict is capped at `LIKELY_VULNERABILITY` unless a fixture-confined oracle also confirms.
2. **Given** a cleanup request that fails, **When** the workflow ends, **Then** the check is `INCONCLUSIVE` (`SEC_CLEANUP_FAILED`), a residual manifest is written by the parent finalizer, and the check is never `NO_ISSUE_DETECTED`.
3. **Given** a kill-switch stop after a mutation was sent, **When** the unit ends, **Then** no cleanup request is attempted, the intent is `RESIDUAL`, and the customer-facing manifest lists the fixture.

### User Story 8 — Fresh, minimal, freshly-authorized reverify (Priority: P2)

A customer marks a security finding fixed. Fahes resolves a new single-unit REVERIFY plan, re-resolves authorization (F01/F07), re-validates credentials, re-runs only the minimal check with fresh evidence and reports PASSED / FAILED / INCONCLUSIVE honestly; it never replays an old exploit blindly.

**Why this priority**: a fix claim is only worth something if it is re-tested under fresh authorization; a stale-credential or stale-grant re-run must not turn into a false PASSED.

**Independent Test**: with only the reverify path wired, reverify one header finding, one authorization finding and one dependency finding against fixtures, once with a valid grant, once with the grant expired, once with the credential revoked; verify fresh single-unit plans, upstream refusal strings passed through verbatim, `INCONCLUSIVE` (never `PASSED`) when anything could not execute, preserved original evidence and linked fresh evidence.

**Acceptance Scenarios**:
1. **Given** a finding whose grant has expired, **When** the customer marks it fixed, **Then** reverify is refused with the upstream reason verbatim and the Issue state is unchanged.
2. **Given** a stored credential that was revoked since the original scan, **When** reverify runs, **Then** the outcome is `INCONCLUSIVE` (`SEC_REVERIFY_UNVERIFIABLE`, underlying `SEC_CREDENTIAL_REVOKED`) and the Issue becomes `UNVERIFIABLE`, never `PASSED`.
3. **Given** a successful minimal re-run that observes the secure behavior, **When** reverify completes, **Then** fresh evidence is linked, the original evidence is preserved, and the outcome is `PASSED`.

### Edge Cases

- Domain verified, active-security grant absent → active checks `BLOCKED` (`NO_MATCHING_GRANT`); passive checks run.
- Grant valid at plan time, expired before dispatch → refused at dispatch by F01 (`EXPIRED`); recorded `BLOCKED`.
- Target reclassified STAGING → PRODUCTION mid-run → F07 stop (`ENVIRONMENT_RECLASSIFIED`); no further request, cleanup NOT attempted, residual manifest emitted.
- Redirect leaves scope → hop refused `SEC_REDIRECT_OUT_OF_SCOPE`; follow-up not made; recorded as observation, not as vulnerability.
- Kill switch fires during a mutating request → request may complete remotely (008 FR-014 named limitation); result not trusted or persisted; fixture marked `RESIDUAL_UNKNOWN`.
- Response body contains a credential or PII → value-aware redaction before any persist; the *fact* that a secret was exposed in a response is itself a finding candidate carrying only a redacted indicator.
- Rate-limit (429) or lockout response → stop that endpoint/identity immediately, record `SEC_RATE_LIMIT_ENCOUNTERED` / `SEC_ACCOUNT_LOCKOUT_RISK`; never retry to "get past" it.
- OpenAPI describes endpoints on a host outside the Target → inventory records them `OUT_OF_SCOPE`; never probed.
- Partial scan (units refused/killed/expired) → module result `DEGRADED`, scored from its findings **with persisted `coverageComplete:false`** (never `COMPLETE`, never presented as complete or as a pass); `null` score only for `NOT_APPLICABLE` (nothing measured).
- Advisory snapshot older than the freshness bound → advisory checks `NOT_TESTED` (`SEC_ADVISORY_STALE`), not PASS.
- Worker crash after a mutating request was sent, before its result was recorded → on recovery the write-ahead intent shows `SENT_UNCONFIRMED`; unit is NOT retried (`attempts: 1`); fixture flagged residual.

## Requirements *(mandatory)*

Reason codes use the closed `SEC_*` registry (plan.md §"Reason-code registry"); no 012 reason is free text. F01/F07/009 reason strings are passed through verbatim, never renamed.

### A — Security Target and Scope Resolution (Context A)

- **FR-001**: Every requested security check MUST be mapped, at plan resolution, to exactly one **check classification** (taxonomy in FR-006), one required F01 `ExecutionClass` (or none for passive), one target, one environment requirement and one boundary set; an unmappable check is recorded `NOT_TESTED` with a closed reason, never dropped.
- **FR-002**: Plan resolution MUST consume 009 `resolvePlan` and 007 `isAuthorized` unchanged. 012 contributes only (a) the domain→class mapping for SECURITY, (b) per-engine unit templates, (c) a precondition predicate that records `SKIPPED`/`BLOCKED` rather than fabricating a pass. 012 introduces no scheduler, graph, authorization service, budget ledger, kill switch or artifact pipeline.
- **FR-003**: Authorization MUST be evaluated freshly at: scan creation (quote), plan resolution, unit dispatch (`safetyCheckpoint`), **every active destination**, **every redirect hop**, **every state-changing step**, and **reverify**. No `AUTHORIZED` result is cached across more than the one action it was obtained for (007 FR-024).
- **FR-004**: 012 MUST route every safety-sensitive action through 008 `safetyCheckpoint` / `requestAdmission` and MUST NOT call `isAuthorized` directly for such an action. Every 012 action type is enumerated as a checkpoint call site in the unit-consumption policy (FR-077; 008 FR-019).
- **FR-005**: A verified domain alone MUST NOT authorize credential use, privilege-escalation tests, stateful mutations, brute-force-shaped repetition, third-party testing or any production active action. Ownership and authorization are consumed as two separate calls (Constitution X; 006 ADR-004).

### Security Testing Classification (taxonomy)

- **FR-006**: The platform MUST classify every check into exactly one of:
  `C0 PASSIVE_OBSERVATION` (no crafted request; derived from responses fetched by `PASSIVE_HTTP`/`BROWSER`/`CRAWLER`, or from 011 static evidence), `C1 NON_MUTATING_ACTIVE` (crafted but read-only request), `C2 CONTROLLED_MUTATING` (state change confined to a registered fixture, reversible), `C3 STATEFUL_AUTHENTICATED_WORKFLOW` (multi-step, session-bound), `C4 POTENTIALLY_DESTRUCTIVE` (**unsupported in v1**), `C5 UNSUPPORTED_HIGH_RISK` (**never supported**: credential attacks, brute force, DoS, data extraction, command execution, third-party testing, production mutation).
- **FR-007**: Classification MUST be computed **mechanically from the probe definition and application semantics**, not from the HTTP method and not self-declared. HTTP GET MUST NOT be assumed harmless (e.g. a GET that triggers a state change is `C2` when the fixture declares it so); POST MUST NOT be assumed destructive (a read-only search POST is `C1`). An operation with no current customer declaration (`ApiOperationDeclaration`, FR-192) is treated as **potentially mutating for every HTTP method**: active probes against it are refused (`SEC_MUTATION_NOT_PERMITTED`) unless the customer declares it read-only or fixture-confined with consent; static checks still run. The registry load step recomputes the class from the probe definition and REJECTS a check whose declared class differs (prevents reclassification to bypass production limits).
- **FR-008**: A check is `C0` **iff** it adds no request beyond what the ordinary passive fetch / 010 browser / 010 crawler already sends unmodified, attaches no credential, and sends no crafted header, parameter, body, method or Origin. `C1` requires `ACTIVE_SECURITY` authorization; `C2`/`C3` (credential or session use: login, logout, refresh, same-identity reads and workflow steps) require `AUTHENTICATED_WORKFLOW` authorization and run in E15; a credentialed *crafted* request — any `NEGATIVE_PROBE` under a credential, and any request under an identity other than the fixture owner against the owner's fixture (cross-identity replay) — requires **both** and runs in E14 under the dual-class rule FR-161.
- **FR-009**: Each check definition MUST declare: required authorization class, allowed environments, required consent flags, maximum request count, mutation policy, session requirements, cleanup requirements, evidence expectations and abort conditions (full list in `security-check-registry-contract`).
- **FR-010**: `C4` and `C5` checks MUST be representable in the registry only as `UNSUPPORTED` entries (so coverage can say "not supported" truthfully); they MUST have no probe definition and no code path.
- **FR-011**: Action categories (the 007 `includedActionCategories` vocabulary 012 defines) are the closed set `READ`, `AUTH_LOGIN`, `AUTH_LOGOUT`, `AUTH_RECOVERY_OBSERVE`, `NEGATIVE_PROBE`, `FIXTURE_MUTATE`, `FIXTURE_CLEANUP`. A check declares exactly which it uses; the `securityScopeGate` refuses an action whose category is absent from the grant's scope when the scope lists categories, and refuses `FIXTURE_MUTATE` unless explicitly listed (a grant with an empty list authorizes `READ` and `NEGATIVE_PROBE` only).
- **FR-012**: `securityScopeGate(identityRef, role, actionCategory, destination)` MUST run before every F07 checkpoint, fail closed, and be covered by conformance tests for each action category (named limitation: not enforced by F01 — see Clarifications).
- **FR-013**: A target with no environment classification MUST refuse every active/authenticated check (`SEC_ENVIRONMENT_UNCLASSIFIED`), never default-permit (007 FR-001).
- **FR-014**: Environment is read from the Target's **current** classification at each check (007 edge case); a reclassification to PRODUCTION blocks subsequent requests via F07 and MUST NOT be "healed" by a later reclassification back.
- **FR-015**: Production behavior per capability MUST be stated in the Production Safety Matrix (plan.md) — every active capability is `RESTRICTED_TO_NON_PRODUCTION`; none requires an upstream amendment.

### B — Secrets and Credential Handling (Context B / F05)

- **FR-016**: Customer-provided testing credentials (kinds supported in v1 are exactly those in FR-027) MUST be stored only as `CredentialVersion` ciphertext under **envelope encryption**: a per-version random 256-bit data key (AES-256-GCM, fresh nonce, AAD binding `{userId, referenceId, versionNumber, secretKind, targetId, kekVersionId}` with a persisted `aadVersion`) wrapped by a Key Encryption Key held in a managed KMS/HSM. No custom cipher or key-derivation scheme is invented. (Provider selection is `UNKNOWN — REQUIRES INVESTIGATION`; any provider MUST offer unwrap-only IAM scoping, key versioning and audit.)
- **FR-017**: Workers, the API and the AI layer MUST NOT hold the KEK or any data key at rest. Only the Credential Broker (FR-031) holds the KMS unwrap permission. Today's shared env `ENCRYPTION_KEY` MUST NOT be used for 012 credentials; `token-vault.ts` is reused only as a *pattern*.
- **FR-018**: Secrets are **write-only** through the product: no API returns a plaintext secret; the UI shows a label, kind, version number, status, creation/expiry times and no secret-derived value of any kind (no prefix, suffix, length or hash).
- **FR-019**: A `CredentialReference` is tenant-owned (`userId`), bound to exactly one `Target`, one environment classification, one `TestIdentity`, and a declared `expiresAt` (finite; platform maximum 90 days; default 30). A reference cannot be used for any other target, tenant or environment.
- **FR-020**: Credentials are **versioned and immutable**; rotation creates a new `CredentialVersion` and marks the prior `SUPERSEDED`; deletion is crypto-shredding (destroy the wrapped data key) plus tombstone; revocation is immediate and one-way.
- **FR-021**: Access control: only the owning user may create/rotate/revoke/delete; operators may **revoke** and **disable** but never read, create or widen (mirrors 007 FR-017). No operator break-glass read exists in v1. Operator actions `revokeAllForTenant`, `revokeAllForKek` and `rewrapAllForKekRotation`, and any KEK disable/delete, require dual control (two distinct operator principals) and raise alerts; KMS key deletion carries deletion protection and a scheduled-deletion delay; broker-host access is logged and restricted. An emergency **single-operator** `disableCredentialReference`/`revokeCredentialReference` for ONE tenant is allowed (audited, alerting) so incident response is not slowed by dual control, which stays mandatory for tenant-wide and KEK operations.
- **FR-022**: Every credential lifecycle event (create, rotate, revoke, expire, delete, broker issue, broker deny, broker destroy) MUST be audited via `AuditLogEntry` (control-plane) and, when tied to an execution, via 008 `recordExecutionAuditEvent` payload — **without secret values**; audit payloads pass the value-aware redactor with the credential's own value registered as a known secret.
- **FR-023**: Retention: ciphertext is deleted at revocation+grace (default 7 days) or expiry+grace; scan evidence that references a `CredentialVersion` id keeps only the id. Incident response: an operator "revoke-all-for-tenant/KEK-version" action MUST exist in the design; a suspected leak triggers revoke, KEK rotation procedure and tenant notification (runbook in quickstart).
- **FR-024**: Raw secret material MUST NOT appear in: `ScanPlan`, `ScanConfiguration`, `ExecutionUnit` (only `credentialBindingRef`), queue job payloads (only `{executionUnitId}`), progress events, logs, Sentry events, `Evidence`, `Artifact`, `Issue`, AI prompts, reports, exports, or screenshots where avoidable (FR-133).
- **FR-025**: Credentials for 012 MUST NOT be reachable from any `SOURCE_EXECUTION` Guest or `apps/sandbox-runner` (Constitution XI; 011 FR-045). Private package registries and other git hosts remain `UNSUPPORTED` until a future spec; 012's vault is designed to accept them later but v1 stores only target-testing credentials.
- **FR-026**: The existing GitHub token vault is unchanged; 012's vault is a separate namespace and table set (no shared columns).
- **FR-027**: Secret kinds supported in v1: `PASSWORD_LOGIN`, `API_KEY_HEADER`, `BEARER_TOKEN`, `SESSION_FIXTURE`. `CLIENT_CERTIFICATE` and `OAUTH_CLIENT_CREDENTIALS` are designed-for but `UNSUPPORTED` in v1 (`SEC_UNSUPPORTED_CREDENTIAL_KIND`).
- **FR-028**: Credential validity checks ("does this credential still work?") are **not** performed by the vault; they occur only inside an authorized execution unit as the first login step, under the same F01/F07 checks and counting against the auth-attempt limit.
- **FR-029**: A credential whose target environment is reclassified to PRODUCTION MUST become unusable immediately (broker re-reads environment per issue).
- **FR-030**: Multi-role accounts: each `TestIdentity` holds one `TestRole` and up to one active credential per kind; role/identity relationships are customer-declared data, never inferred by Fahes.

### C — Credential Broker boundary (F05 delivery)

- **FR-031**: A **Credential Broker** — a minimal, separately deployed trust zone justified by genuine isolation (Principle VIII; repository audit: the worker is over-privileged) — is the only component that can unwrap a data key. It exposes one internal operation `issueCredentialLease(executionUnitId, purpose, attempt, testIdentityId)` (the exact signature of `credential-broker-contract.md`); the requesting worker principal is **derived by the broker from the authenticated connection** (mTLS or workload identity joined to `WorkerPrincipal`, FR-173, FR-201(b)) and is never an argument, a header or any other caller-controlled value.
- **FR-032**: The broker MUST, in one transaction-consistent check against Postgres (never trusting the caller): confirm the unit exists and its status is `RUNNING` — **only `RUNNING`, for both credentialed classes and every caller; the broker never issues for a `PLANNED`, `ADMITTED` or `DISPATCHED` unit** (the lease is requested after `RUNNING`, FR-195, FR-201f), its class is `AUTHENTICATED_WORKFLOW` or `ACTIVE_SECURITY`, its F07 lease is live (an unreleased, unexpired `AdmissionLease` row of the unit; liveness evidence only, the broker receives no holder token), its plan is `RESOLVED` and unexpired (U-1), its scan is non-terminal, its grant is currently `ACTIVE` and lists the class, the Target's environment is non-production, the credential reference belongs to the same tenant and target and is `ACTIVE`/unexpired, the requested identity is a member of the unit's verified credential binding and is within the grant's `includedAccountRefs` and its role within `includedRoles` (each if listed), and no kill switch is pending for any applicable scope. Any failure → deny with a closed reason, audit the denial.
- **FR-033**: Delivery: secret material is returned **only** over an authenticated, tenant- and unit-bound channel to the owning worker's *parent* process, which hands it to the child over IPC into memory only; it is never written to disk, env, command line, queue, log or Redis. Lease `expiresAt` ≤ the unit's remaining `timeoutPolicyMs + hardStopMarginMs` and never more than 30 minutes; non-renewable beyond the unit (a workflow that outlives its lease ends its remaining checks `BLOCKED` / `SEC_CREDENTIAL_EXPIRED`, never re-leases).
- **FR-034**: Workers hold no long-lived secret: no KEK, no data key, no stored plaintext. Parent/child memory is zeroized best-effort on teardown; the design states this is best-effort in a garbage-collected runtime (named limitation) and therefore keeps lease lifetimes short.
- **FR-035**: Every lease is single-purpose and single-unit: `(credentialVersionId, executionUnitId, attempt)` unique; a second issue for the same triple is denied (`SEC_CREDENTIAL_LEASE_ALREADY_ISSUED`) to prevent replay after crash, and recovery obtains a new attempt only where FR-024/009 idempotence is proven (in v1 `maxAttempts: 1` makes this path unused; it is stated so a later idempotence proof does not require a spec change).
- **FR-036**: Credential failure semantics (all produce `BLOCKED` check verdicts and never PASS): `SEC_CREDENTIAL_MISSING`, `SEC_CREDENTIAL_EXPIRED`, `SEC_CREDENTIAL_REVOKED`, `SEC_CREDENTIAL_REJECTED` (target rejected it), `SEC_CREDENTIAL_RATE_LIMITED`, `SEC_MFA_CHALLENGE_UNSUPPORTED`, `SEC_CREDENTIAL_SCOPE_INVALID`.
- **FR-037**: Broker unavailability fails closed: because the lease is requested after `RUNNING` (FR-195(7)), the credentialed checks are `BLOCKED` with `SEC_BROKER_UNAVAILABLE` and, when no step can run, the unit is finalized `COMPLETED` through `sec_finalize_unit` (never `REFUSED`: 009 has no `RUNNING->REFUSED` edge); there is no fallback path that reads the vault directly.
- **FR-038**: The broker MUST NOT make outbound requests to targets, and MUST NOT log request bodies; its telemetry contains ids and outcomes only.
- **FR-039**: Revocation, expiry, grant revocation or kill switch MUST destroy outstanding leases: the broker marks the lease `REVOKED`; the engine detects this at each checkpoint (≤ 5 s cadence) and tears down; the broker also exposes `confirmLeaseDestroyed(leaseId)` which the engine's `onUnitExpired` hook uses to return `TERMINATED` only after the session is provably invalidated (FR-052). **Before every request** the parent reads the lease status from the broker (`getLeaseStatus`, timeout <= 1 s) as a precondition of minting the request permit (FR-190); there is no revoke-push channel (the broker has no network path to workers); a status read that errors, times out or returns `REVOKED`/`EXPIRED` admits no request (no permit is minted), so no further request is sent (`SEC_BROKER_UNAVAILABLE` for error/timeout, the lease reason otherwise); at most the in-flight request(s) already permitted (<= the unit's in-flight limit) follow a revocation commit.
- **FR-040**: The broker is behind activation gates SG3 and SG10 (plan.md); in v1 it is a hard prerequisite for any credential use; absent broker ⇒ all credentialed checks `BLOCKED`.

### D — Authenticated Session Management (Context C)

- **FR-041**: A `SessionHost` lives inside the E15 (and E14 when authenticated) child process and owns: login, cookie/token jar, renewal, expiry detection, logout and teardown. It is **execution-local state** (never persisted, never serialized, never shared across units). The jar lives in the child (the secret already is there), but **the child decides nothing about authorization**: the identity, role, action category and every other authorization input of a request come from the parent-held plan step (FR-200), the parent runs `securityScopeGate` for every frame, and a `CREDENTIAL` slot value is accepted only if it is an exact-value-registered secret of **that step's** identity. A child-side identity/role or gate result is never trusted.
- **FR-042**: A session is bound to exactly one `(executionUnitId, attempt, testIdentityId)`; two identities in one unit use two isolated `SessionHost` jars; sessions MUST NOT mix tenants, customer environments, roles, browser profiles or scans.
- **FR-043**: A session MUST NOT outlive its authorization: at every checkpoint the host verifies grant/lease/scan/deadline/broker-lease liveness; failure ⇒ immediate local invalidation (drop jar, attempt server-side logout only if an admission is still obtainable — otherwise record `SEC_SESSION_NOT_SERVER_INVALIDATED`).
- **FR-044**: Session expiry/renewal: refresh only via the identity's own credential (re-login) or its refresh token; each re-login counts against the auth-attempt limit; renewal never extends beyond lease/unit/grant bounds.
- **FR-045**: Logout and cleanup run on every exit path within the unit's `timeoutPolicyMs` (budgeted per 009 `execution-unit-contract` rule 6): complete, fail, cancel, kill (best-effort, see FR-043), deadline, crash recovery.
- **FR-046**: Crash recovery: a recovered unit never reuses a prior attempt's session or lease; any server-side session that cannot be confirmed destroyed is recorded in the unit's `CleanupRecord` as `SESSION_UNCONFIRMED` with its expected natural expiry.
- **FR-047**: Session artifacts (cookie jars, tokens) MUST NOT be persisted as Evidence; only redacted metadata (cookie names, flags, lifetimes, token *type* and length class) is recorded.
- **FR-048**: Authenticated browsing (browser storage state injection) is `UNSUPPORTED` in v1 (Clarifications; AR-2).
- **FR-049**: Session fixation indicator checks compare pre- and post-login session identifiers by value-agnostic comparison (hash comparison inside the host; only the boolean and cookie name are recorded).
- **FR-050**: Customer-provided session fixtures (`SESSION_FIXTURE`) carry a declared `expiresAt` and are treated as credentials (FR-016) — they are never extended.
- **FR-051**: Concurrent identity sessions per unit ≤ 4; per tenant per target concurrency is bounded by the grant's `concurrencyBudget` (F07).
- **FR-052**: Every non-passive engine registers `onUnitExpired(unit) → TERMINATED | PENDING` (009 U-1) and returns `TERMINATED` only after `confirmLeaseDestroyed` and local jar disposal; it also declares `hardStopMarginMs` and an independent hosting-failure backstop (F1: the parent is not the only authority able to terminate execution or end a credential; the absolute hard TTL, the broker lease expiry, the child-side deadline and the execution-plane orphan reconciler, the seven-case crash matrix and its enforceable bounds are in data-model 4.10F; activation is blocked until the 009 / SPEC 011 backstop is approved and implemented, AR-22).

### E — Active Security Probe Engine (E14) and Authentication Workflow Engine (E15)

- **FR-053**: E14 is an engine under 009 class `ACTIVE_SECURITY`, queue `webaudit-exec-active-security`, `engineId` family `security.active.*`; E15 is under `AUTHENTICATED_WORKFLOW`, queue `webaudit-exec-authenticated-workflow`, `engineId` family `security.auth.*`. Each unit runs in a dedicated child process (009 FR-019) with a parent-side unconditional SIGKILL.
- **FR-054**: Both engines send requests **only** through a `SecurityHttpClient` built on `@webaudit/safe-net` (never global fetch, never a second HTTP stack), extended (implementation task, not a frozen-spec change) to expose multi-value response headers, per-request timing and an `AbortSignal`, and to *forbid* automatic cross-origin redirect following. safe-net's four SSRF layers and sensitive-header stripping remain unchanged.
- **FR-055**: Every request: (0) a child frame `{stepId, credentialSlots[]}` resolved by the parent to an immutable plan step (FR-200); (1) admission in the FR-190 order — Phase A side-effect-free reads including `securityScopeGate`, Phase B releasable reservations including the local budget `reserve`, Phase C `safetyCheckpoint(consumes{request:true, concurrency:false})` ⇒ PROCEED as the last and only irreversible step, (2) mutation write-ahead intent if `C2`, (3) the parent renders the request from the step and slot values and the gate serializes and sends it (FR-175, FR-199, FR-200) composed with the checkpoint's `AbortSignal`, (4) bounded body read, (5) redact-then-record Evidence through the engine's fenced writer. The order is invariant.
- **FR-056**: The checkpoint cadence while a request or workflow is in flight is ≤ 5 s (008); a long idle wait (e.g. waiting for an MFA fixture window) is a polling loop with checkpoints.
- **FR-057**: Retry policy: `ACTIVE_SECURITY` and `AUTHENTICATED_WORKFLOW` units default to `retryPolicy.maxAttempts: 1` (009 FR-024). A retry of any non-idempotent request is forbidden; a retry of a proven-idempotent `C0/C1` request is permitted only if the check definition declares `idempotent: true`, each retry consumes F07 budget and a new `idempotencyKey`, and the retry count is bounded by the local retry limit.
- **FR-058**: Unit-produced Evidence is written only through the engine's **fenced evidence wrapper** ("fence first, claim second, write third" — 009 U-1), which refuses writes for a terminal unit, terminal scan or passed deadline; a test MUST prove every unit-produced write goes through it. The fence predicate also requires no pending `KillSwitchState` for the unit, its scan or its grant (parent-derived residual manifests are exempt, FR-162).
- **FR-059**: Cancellation: user cancel → F07 `USER_CANCELLATION` → unit `CANCELLED`; operator/safety stop while `RUNNING` → `KILLED`; a stop or refusal **before** `RUNNING` is `REFUSED` with the F07 reason (009's table has no pre-run `KILLED` edge, FR-195, AR-18); 012 never maps a measured security result to `FAILED` (a successful probe, a 401 or a 403 is `COMPLETED` with evidence; 009 R9a). `FailureClass.TARGET_UNAVAILABLE` covers a target that broke; `CUSTOMER_CODE_FAILURE` is not used; `FAILED` is used only when **no probe of the unit completed**, and a mid-run credential revocation ends the unit `COMPLETED` (affected checks `BLOCKED`) when at least one probe completed.
- **FR-060**: Failure of a `SecurityHttpClient` request (timeout, reset, TLS error) is evidence, not a PASS and not an exception that aborts unrelated checks: the affected check records `INCONCLUSIVE` (`SEC_RESPONSE_AMBIGUOUS`) or `BLOCKED` (`SEC_SAFE_NET_REFUSED`).
- **FR-061**: Each unit declares `timeoutPolicyMs` including setup, login, work, persistence, cleanup and finalization; `hardStopMarginMs` default 60 000; initial calibrated values are in plan.md §"Unit timing"; they are provisional until measured (009 U-1: `M` calibration before activation).
- **FR-062**: A composite test (e.g. IDOR needing two identities and an adversarial request) generates **one unit per class** linked by an `ExecutionDependency` edge that gates *ordering and baseline validity only* (e.g. "do not run the cross-identity probe if the identity baseline login failed"); it does NOT pass a session between units — each unit obtains its own lease and session from the broker. A credentialed *crafted* request issued by an E14 unit is governed by the dual-class rule (FR-161). This resolves 006 decisions.md l.160.
- **FR-063**: Runtime discovery of new endpoints during a unit MUST NOT create units outside the plan; additional endpoints are recorded as `API_SURFACE` observations and tested in a later, separately authorized plan.
- **FR-064**: Engines never self-declare Finding attribution or fingerprints; the runner assigns attribution; fingerprints use 009's `fingerprintOf` (FR-141).
- **FR-065**: The engines contain no AI calls (Constitution III; 009 FR-046).
- **FR-066**: A probe definition is data: `{method, pathTemplate, parameters, headers (closed set), body (typed, from a harmless alphabet), expectedObservation, oracle}`; it is versioned and vendored locally (Principle II). No payload corpus downloaded at runtime, no runtime-evaluated code in a probe.
- **FR-067**: Engines MUST refuse a probe whose rendered request would exceed `maxRequestBytes`, `maxHeaderCount` or whose destination host differs from the target's authorized hosts.
- **FR-068**: Engines MUST NOT execute customer code; dynamic tests that would require running customer code against a live target are out of scope; running customer source goes only through 011's Provider Port under AG1–AG10 and never receives 012 credentials.

### F — Request Budgets and Rate Control

- **FR-069**: F07 stays authoritative for **request count** (cumulative per grant), **concurrency** (leases, 30 s TTL, fenced) and **duration** (grant `expiresAt`). 012 MAY set tighter per-class ceilings (007 FR-011) and does: initial provisional ceilings in plan.md §"Budgets".
- **FR-070**: Engine-local limits (each pre-checked **before** the request is issued, not counted afterwards): total requests per unit; per-endpoint; per-identity; per-workflow; concurrent in-unit requests; authentication attempts (reserved through the broker, FR-191); redirect depth (default 0 cross-origin; ≤ 3 planned same-origin hops); response body bytes per request (default 256 KiB read cap); total response bytes per unit; execution duration; retries; mutations per fixture and per unit; per-unit request ceilings and in-flight counts (F07 grants one concurrency lease per unit, so more than one in-flight request is local). Each is labeled "LOCAL — not F07-ledgered". Authentication attempts are **reserved through the broker before every login/refresh** (FR-191) in a rolling window per `TestIdentity` (provisional 24 h) across scans and reverify: failed attempts (limit **3**, hard maximum 5) are counted separately from the ceiling on total SENT attempts (provisional 12), successful logins do not count toward the failure limit, and a customer-declared `lockoutThreshold` caps failures below the target's own threshold. Decoded response size is capped (decoded bytes and decompression ratio; truncate-and-flag, never throw) and JSON depth/key-count limits apply before parsing.
- **FR-071**: Local limits are enforced by a single `LocalBudget` object consulted by `SecurityHttpClient` before the network call; every counter is taken by an atomic `reserve` (increment-and-check) and returned by `release` for a request never sent; per-endpoint, per-identity and byte counters for credentialed units are read from a durable per-plan source so concurrent hosts cannot each spend the full allowance; there is no code path that sends without consulting it; retry logic consumes budget like any request.
- **FR-072**: Request-count accounting policy ("what is one request"): one outbound HTTP request, including each redirect hop and each retry, equals one F07 request unit. This is the unit-consumption policy required by 008 FR-019 and is declared in `active-security-execution-contract`. **Every checkpoint call carries its own deterministic `idempotencyKey = H(unitIdempotencyKey, callSite, requestOrdinal | probeClaimKey, redirectHopIndex)`**: the unit-level key is used only for the dispatch checkpoint, each retry and each redirect hop has a distinct ordinal, the secondary dual-class check uses `H(primaryKey, "SECONDARY")`, and a redelivered request with the same ordinal replays the same F07 result without a second consumption (008 replay semantics). The call-site names in FR-077 are audit-payload and idempotency-key labels, not `safetyCheckpoint` parameters. Request ordinals are **parent-assigned and monotonic, never child-supplied** (FR-190).
- **FR-073**: Rate pacing: a minimum inter-request delay per host (default 250 ms for `C1`, 500 ms for `C3`) applied before checkpointing; a 429 or `Retry-After` pauses that endpoint+identity for the remainder of the unit.
- **FR-074**: Lockout protection: after any response that matches the closed lockout-signal set (status 423, `Retry-After` on login, "account locked" body class), all further authentication attempts for that identity in the scan are blocked (`SEC_ACCOUNT_LOCKOUT_RISK`).
- **FR-075**: Infinite-loop safety: every workflow is a finite DAG of ≤ 25 steps with no unbounded loops (the cap is 25 everywhere; there is no larger hard cap); a probe family iterates over a finite, registry-declared input list.
- **FR-076**: Budget exhaustion ends the affected check as `BLOCKED` (`SEC_BUDGET_LOCAL_REQUESTS` etc. or F07 `BUDGET_EXHAUSTED_REQUEST`) and never as PASS.
- **FR-077**: Each engine declares its unit-consumption policy (008 FR-019) before `/speckit-tasks`: the action types that are checkpoint call sites are `HTTP_REQUEST`, `REDIRECT_HOP`, `LOGIN_ATTEMPT`, `LOGOUT`, `FIXTURE_MUTATION`, `FIXTURE_CLEANUP`, `SESSION_REFRESH`.

### G — Production Safety, Destination Safety and SSRF

- **FR-078**: Production: no 012 `ACTIVE_SECURITY` / `AUTHENTICATED_WORKFLOW` unit is ever created or dispatched against a PRODUCTION or unclassified target. Enforcement at plan resolution (domain-class filter), at the broker (FR-032), at `securityScopeGate` (FR-012) and at dispatch (F01 FR-015a already refuses the grant itself). A check is never silently relabeled passive to bypass this (FR-007 mechanical classification).
- **FR-079**: Destinations: every request destination (initial, redirect hop, OpenAPI server URL, any URL embedded in a probe) is checked with `isInScope` via checkpoint **and** passes safe-net layers 1–4. Cloud metadata, link-local, loopback, RFC1918, alternate IP encodings, IPv6-mapped forms, DNS rebinding and proxy tricks are refused by safe-net's connect-guard. 012 adds no allow-list entry and never sets `SAFE_NET_ALLOW_TARGETS` outside tests.
- **FR-080**: A security check MUST NOT test the customer's SSRF behavior by making Fahes itself request a prohibited destination. SSRF indicators are limited to: (a) static signals (011 `SOURCE_SURFACE` URL-fetching sinks), (b) spec-based observations (parameters named/typed as URLs, `format: uri`), and (c) **canary-callback-free** response analysis against in-scope URLs. Out-of-band (OAST) interaction is `UNSUPPORTED` in v1. Two named, bounded exceptions to the "no URL/file reference" canary rule exist: (i) a URL-typed parameter may carry an `isInScope`-validated in-scope URL (never external), and (ii) CORS probes send an inert `Origin` header form (FR-110).
- **FR-081**: Redirects: default policy is *do not follow cross-origin*; same-origin hops are followed only as planned `REDIRECT_HOP` steps (FR-200(e)) and re-admitted at each hop (FR-003); a redirect to an out-of-scope destination is recorded as an observation (`SEC_REDIRECT_OUT_OF_SCOPE`) and not followed; "same-origin" means identical scheme+host+port; every credential-class header (registry-declared injection header names plus `Authorization`, `Cookie`, `Proxy-Authorization`, `X-*-Token`, `X-API-Key` and any name matching the structural rule of FR-128) is stripped **by `SecurityHttpClient`** on any non-identical origin — today's safe-net strips only `authorization`, `cookie` and `proxy-authorization` and keys "same enough" on host, a gap that is closed by implementation tasks, not assumed; an https→http hop is refused outright.
- **FR-082**: Third-party resources reached by a page (scripts, APIs) are never probed; CORS/CSP observations about them are passive observations only.
- **FR-083**: The probe never accepts a destination from response content, an OpenAPI `servers` entry or a customer-controlled redirect without passing FR-079; the OpenAPI `servers` list is inventory data, never a request target by itself.
- **FR-084**: OpenAPI parsing is offline: external `$ref`, `file:`, `http(s):` and `data:` references are refused (`SEC_API_SPEC_EXTERNAL_REF_REFUSED`); spec size ≤ 5 MiB, depth ≤ 64, node count ≤ 200 000; YAML anchors/aliases bombs and recursive refs are bounded and rejected. Parsing runs in an isolated `worker_threads`/child context with `resourceLimits`, no network and a hard terminate at 10 s; alias/anchor/merge-key expansion is pre-scanned at byte level before the library runs; object keys are handled prototype-pollution-safe.
- **FR-085**: Browser-based security observations use 010 `BROWSER` units only and 010's safe-net proxy; no duplicate browser runtime; they are unauthenticated and non-mutating in v1.

### H — Authentication Testing Domain (Context F)

- **FR-086**: Auth checks (`auth.*`) cover: login success/failure behavior, session creation, cookie flags on session cookies, session invalidation on logout, expired-session handling, session-fixation indicator, CSRF protection on session-bound state-changing endpoints (observed via fixture comparison), account-recovery flow **structure** (presence and shape of the flow; no token guessing), MFA enforcement observations, authentication error uniformity (user enumeration indicator via a **single** differential pair on registered identities only), and authorization after logout.
- **FR-087**: The platform MUST NOT implement password guessing, credential stuffing, account takeover, token brute-forcing or recovery-token guessing (`C5`).
- **FR-088**: Account-recovery checks MUST NOT trigger email/SMS to real recipients: they run only when the customer registers a recovery fixture (test mailbox/sink owned by the customer) and the grant lists `AUTH_RECOVERY_OBSERVE`; otherwise `NOT_TESTED` (`SEC_SIDE_EFFECT_FIXTURE_MISSING`). Side effects (lockout, email, SMS) are enumerated per check in the registry (`sideEffects[]`). Identity registration records an attestation that login and notification emails/SMS for the identity go to customer-owned sinks only; login checks require it.
- **FR-089**: Every auth check states an explicit expected outcome; an unexpected-but-benign outcome is `INCONCLUSIVE`, never `FINDING`.
- **FR-090**: MFA: v1 modes per Clarifications; the engine records "MFA challenge observed" as an observation, never attempts bypass, enforces a challenge timeout (default 120 s) and retry limit (1), preserves session continuity only inside the unit, and reports `SEC_MFA_CHALLENGE_UNSUPPORTED` or `SEC_MFA_TIMEOUT` as `BLOCKED`.

### I — Authorization Testing Domain (Context G)

- **FR-091**: Authorization checks (`authz.*`) cover RBAC, resource ownership (object-level, BOLA/IDOR), function-level (BFLA), tenant boundaries, horizontal separation and vertical privilege boundaries — **only** against customer-registered identities and `FixtureResource` records.
- **FR-092**: The platform MUST NOT enumerate or guess identifiers, access third-party data, or touch any resource not registered as a fixture; object identifiers used in a probe come exclusively from `FixtureResource.identifiers`; response-derived identifiers are never used in v1 (a `RESPONSE_DERIVED` slot is a token slot and never carries an object identifier; a redirect `Location` can only select among identifiers the plan already lists; FR-200(d)(e)), and a collection locator is refused unless the fixture declares `collection:true` with a maximum size.
- **FR-093**: Customers declare an `AuthorizationExpectation` matrix: for `(role | identity) × (endpoint-or-operation) × (fixture-resource-owner)` the expected outcome class (`ALLOW`, `DENY`, `DENY_OR_NOT_FOUND`). Observed outcome classes are compared pairwise; the comparison uses status class **and** a response-shape oracle (e.g. fixture marker present/absent), never status alone.
- **FR-094**: Outcomes are separated: `CONFIRMED_VULNERABILITY` (expectation says DENY, observed ALLOW, oracle confirms the fixture's marker was returned/changed); `LIKELY_VULNERABILITY` (status indicates allow, oracle unavailable); `INCONCLUSIVE` + `SEC_FIXTURE_LIMITATION` (insufficient identities/resources); `UNSUPPORTED` (`SEC_UNSUPPORTED_TARGET_TYPE`); `NO_ISSUE_DETECTED` (only for executed pairs, scoped in the statement); expected `ALLOW` but observed `DENY` ⇒ `INFORMATIONAL` (a possible fixture or expectation error, not a vulnerability); a `2xx` whose oracle marker is absent with a valid baseline ⇒ scoped `NO_ISSUE_DETECTED`; a `404` under strict `DENY` ⇒ `INFORMATIONAL`.
- **FR-095**: Vertical tests use only a customer-registered low-privilege identity attempting customer-listed privileged operations; the platform MUST NOT use or request an administrative credential that the customer has not registered for that purpose, and an admin identity is used only as the *owner* of a fixture, never as an attacker. Identities default to `usage = UNSET`, which is not selectable as an actor; actor use requires explicit `ACTOR_ALLOWED`; a role with the highest `privilegeTier` (or an unset tier on a multi-role target) is treated as high-privilege, and an empty `includedAccountRefs` never authorizes a high-privilege or `UNSET` identity.
- **FR-096**: Mutating authorization probes (e.g. attempt to modify another identity's fixture) are `C2`, require `FIXTURE_MUTATE`, and follow Mutation & Cleanup (Context M).
- **FR-097**: Tenant-boundary tests require two customer-registered tenant fixtures in the **same** Fahes tenant/Target; Fahes never tests across Fahes tenants.

### J — API Discovery and API Security (Context H)

- **FR-098**: API surface discovery produces `API_SURFACE` Evidence (parent-side, no network) from: customer-provided OpenAPI (stored as a tenant-scoped Artifact), 011 `SOURCE_SURFACE` (with `surfaceComplete`), and observed authorized traffic (`HTTP_TRANSACTION`/`HAR` from 010 units). Each entry preserves `apiIdentity`, method, path template, parameters, request/response schema refs, authentication requirements, scope verdict, environment and `origin` (`OPENAPI|SOURCE_DERIVED|OBSERVED`).
- **FR-099**: Joining a runtime URL to a 011 `RouteIdentity` MUST supply the service/workspace key; an unresolvable join is recorded `surfaceComplete: false`, never guessed (011 correlation rule); 012 does not redefine identity grammars.
- **FR-100**: **Discovery is not authorization.** `API_SURFACE.scopeVerdict ∈ {IN_SCOPE, OUT_OF_SCOPE, UNAUTHORIZED_CLASS}` is computed with `isInScope`/class availability (no request; a destination of a prohibited class is `OUT_OF_SCOPE` with `SEC_DESTINATION_PROHIBITED`) and an endpoint is *probe-eligible* only if `IN_SCOPE` **and** the active grant lists the needed class **and** action category.
- **FR-101**: API checks (`api.*`) separate **static/spec-based analysis** (`C0`: undefined auth on write operations, schemes missing, response schemas exposing sensitive-named fields, missing rate-limit documentation, deprecated/versioned path coexistence) from **active requests** (`C1`+: unauthenticated access to an operation the spec says requires auth, authorization boundaries, request-validation behavior, response data exposure vs schema, error handling disclosure, CORS behavior, rate-limit header observation, schema-violation handling).
- **FR-102**: Active API probes are structured, versioned definitions derived from the operation schema and a closed *harmless alphabet* (boundary values within schema type: empty/absent optional, max-length ±1 within a bounded cap, wrong type, extra property, unexpected content type); **no fuzzing**, no random mutation, no corpus. Maximum probes per operation: 8 (provisional).
- **FR-103**: Rate-limit observation is passive-by-default (headers, spec); an *active* rate-limit probe is `UNSUPPORTED` in v1 (it would approach load/DoS; SPEC 013's domain).
- **FR-104**: Response-exposure checks compare the response against the declared schema and the sensitive-field classifier on **recorded, redacted** shapes (field names/types and value-class flags), not stored values.

### K — Probe families: injection, XSS, CSRF, configuration, dependencies

- **FR-105**: Injection/input-validation indicators (SQL, NoSQL, command, template, path traversal, unsafe deserialization, XSS) MUST prefer, in order: (1) static evidence (011 `SOURCE_SURFACE`/`CODE_FLOW`), (2) spec-derived expectations, (3) harmless bounded canary inputs, (4) non-destructive response observation. The canary alphabet is closed, inert (e.g. `fh12ab"'<>` markers with a unique per-probe token) and contains no executable payload, no time-delay primitive, no file or network reference, no command separators intended to execute and no data-extraction construct.
- **FR-106**: A weak signal is not proof. Verdict ladder for injection indicators: reflected/echoed unescaped canary in an executable context ⇒ `LIKELY_VULNERABILITY`; DBMS/engine error signature in response to a malformed-quote canary ⇒ `LIKELY_VULNERABILITY` (never `CONFIRMED` — confirmation would need data-dependent behavior change that requires unsafe activity); generic 500 ⇒ `INCONCLUSIVE` (`SEC_SIGNAL_WEAK`); escaped/neutralized ⇒ `NO_ISSUE_DETECTED`. When reliable confirmation would require unsafe activity the report states the limitation (`confirmationLimitation` field). **v1 scope**: because the closed canary alphabet can only express reflection and malformed-quote behavior, command-injection, template-injection, path-traversal, unsafe-deserialization and NoSQL *active* probes are `SEC_PROBE_CLASS_UNSUPPORTED` in v1 (static/spec-derived signals from 011 and spec analysis only).
- **FR-107**: XSS: static (011 sinks), escaping/context observation of the unique canary, CSP observations, DOM source→sink indicators through 010 browser evidence on unauthenticated pages; no script that exfiltrates, no cookie access, no action on behalf of a user; the canary is inert (no `<script>` that executes anything; context-escape *markers* only).
- **FR-108**: CSRF: token presence/lifecycle observations, `SameSite`/cookie attributes, `Origin`/`Referer` enforcement observation using a *safe fixture comparison* (same fixture request with and without token/origin against a customer-registered fixture endpoint that is non-mutating or fixture-confined). Token absence alone is `CONFIGURATION_RISK`/`INFORMATIONAL`, **never** "exploitable CSRF"; no destructive operation is triggered to prove CSRF.
- **FR-109**: Security configuration checks (TLS-visible, certificate validity, HSTS, CSP, CORS, cookie attributes, security headers, HTTP method exposure, error/debug disclosure, cache-control on authenticated/sensitive responses, sensitive-endpoint exposure) separate `CONFIGURATION_RISK`, `INFORMATIONAL` and (only with proof) `CONFIRMED`; real TLS inspection (protocol, ciphers, chain, expiry) requires a guarded raw-socket door in safe-net and is a NEW engine facility gated by a distinct task; until then TLS-detail checks are `NOT_TESTED`/`UNSUPPORTED` (`SEC_TLS_INSPECTION_UNAVAILABLE`). Checks owned by 010 (SEO, accessibility, functional) are not duplicated.
- **FR-110**: CORS observation: a probe with a crafted `Origin` is `C1` (active, non-production only); passive CORS observation from ordinary responses is `C0`. A reflected arbitrary origin with credentials allowed is `CONFIGURATION_RISK` (HIGH cap) and `LIKELY` only if both `Access-Control-Allow-Origin` reflection *and* `Allow-Credentials: true` are observed for a registered-identity authenticated endpoint **and** the session credential is a cookie with `SameSite=None` (or declared); Bearer/header credentials and Lax/Strict cookies cap at `CONFIGURATION_RISK`.
- **FR-111**: Dependency advisory matching consumes 011 `DEPENDENCY` evidence (lockfile-resolved versions; transitive via lockfile; `UNSUPPORTED` ecosystems recorded) against an `AdvisorySnapshot` with provenance (source, import time, snapshot digest, signature) and a freshness bound (provisional 14 days). No network lookup at scan time. A vulnerable version alone is a `CONFIGURATION_RISK`/`LIKELY` *advisory match*, never "exploitable"; reachability claims require 011 `CODE_FLOW` evidence and are otherwise stated as unknown. Fix versions are suggested only when the advisory data states an unambiguous patched range.
- **FR-112**: An unresolved version (range without lockfile) is `NOT_TESTED` (`SEC_VERSION_UNRESOLVED`); a stale snapshot is `NOT_TESTED` (`SEC_ADVISORY_STALE`); false-positive handling uses a customer-owned suppression recorded as audit data and never deletes the finding (Issue lifecycle states belong to F03/006 FR-017).
- **FR-113**: Secret-in-source/page detection remains the existing `data-leak-scanner` (REUSE, extended to JS bundles and API-response bodies); 012 adds no secret *validity* testing (no live-key validation).

### L — Business-Logic Security Domain (Context I)

- **FR-114**: Business-logic checks (`logic.*`) run only against customer-defined **`BusinessInvariant`** records or trusted application contracts (OpenAPI constraints) and only on non-production fixtures; with no invariant there is no verdict (`SEC_INVARIANT_UNDEFINED`).
- **FR-115**: The invariant vocabulary is a closed, declarative predicate set over recorded observations: `EQUALS`, `NOT_EQUALS`, `SUM_EQUALS`, `MONOTONIC_STATE_TRANSITION(allowedGraph)`, `AT_MOST_ONCE(actionKey)`, `NON_NEGATIVE`, `WITHIN_QUOTA(n)`, `IDEMPOTENT(actionKey)`, `OWNER_ONLY`. No scripts, no regex-from-customer, no code.
- **FR-116**: An unusual-but-possible workflow is not a vulnerability: a violation requires an invariant evaluated to `false` on observations from an executed bounded workflow. Predicates are evaluated inside the engine child over transient in-memory observations; only the predicate id, boolean outcome and *class-level* values (`recordMode: CLASS_ONLY`, or `VALUE_RECORDED` for customer-declared non-sensitive fields) are persisted (FR-128/131 forbid persisting raw values). A verdict from an engine-evaluated invariant is capped at `LIKELY_VULNERABILITY`; `CONFIRMED` additionally requires a fixture-confined oracle (FR-140). `VALUE_RECORDED` values pass the value-aware redactor and PII-pattern scan, are length/type capped, and are refused for any field matching secret/PII detectors.
- **FR-117**: Workflows are customer-declared finite step lists (≤ 25 steps) referencing fixture resources and the closed `actionCategory` set; payment, refund, purchase, inventory and messaging endpoints are usable only if the customer maps them to a **sandbox/fake fixture endpoint** and marks them `SANDBOX_CONFIRMED`; Fahes cannot verify that claim and states "customer-asserted fixture safety" in the report (named limitation). Sensitive-class workflows require an **interactive per-run typed re-confirmation recorded as an audit event (`run.sensitive_confirmed`) and checked at dispatch; non-interactive runs (scheduled, CI-triggered, API-triggered without the event) refuse sensitive-class workflows (`SEC_CONSENT_MISSING`)**; the live-mode tripwire is only a backstop with recall limits, not the control: any response carrying a live-mode indicator (live-key patterns already detected by `@webaudit/redaction`, `livemode`-class fields) aborts the workflow with `SEC_MUTATION_NOT_PERMITTED`.
- **FR-118**: Duplicate-action, idempotency and quota invariants are tested with a **bounded** number of repeats (provisional ≤ 3 total executions per action key, which equals the per-fixture mutation ceiling), never a race-condition flood; timing-based race testing is `UNSUPPORTED` in v1.

### M — Mutation and Cleanup

- **FR-119**: Every `C2` step MUST declare: explicit authorization (`FIXTURE_MUTATE` in scope + per-mutation-class consent), fixture identity, expected mutation, max mutation count, idempotency identity, cleanup method, cleanup verification, failure handling, retry behavior (none) and residual side effects.
- **FR-120**: **Write-ahead intent**: before sending any `C2` request the engine records a `CleanupRecord` row-equivalent (execution-local state flushed to a durable `MutationIntent` in Postgres through the fenced writer) with `state` ∈ `INTENDED → SENT → CONFIRMED | SENT_UNCONFIRMED` (or `ABANDONED` if never sent) and `cleanupState` ∈ `NOT_REQUIRED | PENDING | REVERTED | RESIDUAL`, where `RESIDUAL` carries a closed `residualReason` ∈ `CLEANUP_FAILED | CLEANUP_UNVERIFIED | ADMISSION_REFUSED | SENT_UNCONFIRMED | MANUAL_REQUIRED`; the terminal cleanup states are `REVERTED` and `RESIDUAL`. Recovery uses it to avoid duplicate mutation and to produce the residual manifest.
- **FR-121**: Cleanup is performed by an authorized `FIXTURE_CLEANUP` request in the same unit (local pre-reservation of **3** request units per mutation: the mutation, the cleanup and the verification read; F07 has no reservation primitive, so this is local accounting — an unreservable verification yields `SEC_CLEANUP_UNVERIFIED`) or by the customer-declared fixture-reset mechanism; success is **verified** by a read of the fixture state.
- **FR-122**: **No cleanup after a stop.** After any F07 stop (`REQUESTED|ACKNOWLEDGED|STOPPED`) or grant revocation, admission is refused (`KILL_SWITCH_PENDING`); the platform MUST NOT attempt out-of-band cleanup. It emits a **Residual Manifest** (fixture ids, last confirmed state, expected manual action) as Evidence (`CLEANUP_RECORD`, state `RESIDUAL`), written by the parent-side finalizer from durable `MutationIntent` rows (FR-162), because the unit's fenced writer refuses writes after a stop and the check is `INCONCLUSIVE` (`SEC_CLEANUP_FAILED`/`SEC_CLEANUP_UNVERIFIED`).
- **FR-123**: A test MUST NOT be marked `NO_ISSUE_DETECTED` if its required cleanup failed or is unverified; a `CONFIRMED`/`LIKELY` finding from a step whose cleanup failed is kept, with the cleanup state attached.
- **FR-124**: Cancellation does not reverse already-issued requests (008 FR-014 named limitation); reports state this.
- **FR-125**: Mutation counts: per fixture ≤ 3 (enforced per scan plan by the database through the unique `MutationIntent.mutationOrdinal`, MA-06), per unit ≤ 10 (provisional), and the grant's request budget; per-mutation-class consent defaults OFF (Clarifications).
- **FR-126**: Fixture resources are customer-registered, tenant-scoped, environment-scoped records (`FixtureResource`) with owner identity, resource locator template, reset method and a `maxMutations`; Fahes never creates fixtures on the target implicitly (creation is itself a `FIXTURE_MUTATE` step declared in a workflow).

### N — Evidence, Privacy, Redaction

- **FR-127**: All 012 Evidence is written through 009 `recordEvidence` / `createArtifact`; units of class `ACTIVE_SECURITY` / `AUTHENTICATED_WORKFLOW` get mandatory redaction (009 FR-030). 012 additionally runs a **value-aware redaction pre-pass** (FR-128) and applies the same redactor to any parent-side derived evidence (`API_SURFACE`, `SECURITY_CHECK_RESULT`, `ADVISORY_MATCH`) and to any 012 evidence produced under `BROWSER`/`CRAWLER`/`PASSIVE_HTTP` (010 FR-045 gap).
- **FR-128**: Redaction MUST NOT rely on field names alone: (a) exact-value registration of every secret in play (credential values, issued session tokens, CSRF tokens, response-set cookie values) before any request, (b) `@webaudit/redaction` pattern/entropy detection, (c) structural rules: all `Cookie`/`Set-Cookie`/`Authorization`/`Proxy-Authorization`/`X-*-Token`-class header **values** and all URL query values are replaced by typed placeholders (`<redacted:cookie lenClass=M>`, a bucket never an exact length), (d) body minimization: store shapes, a non-secret structure hash (over key/type structure, never over values), length classes and ≤ 600-char post-redaction excerpts (unauthenticated responses only), never full bodies, (e) header/cookie/JSON-key/query-parameter **names are values too**: they pass the pattern/entropy detectors and a name-class allow-list (value-bearing names become `<name:class>`), and a PII detector set (email, phone, card number with Luhn, IBAN, national-id formats) runs on excerpts; `excerptAllowed` defaults to false except for header/CSP-class checks. A response may contain secrets the request did not.
- **FR-129**: A redaction failure writes `{"_redactionFailed": true}` and never the raw payload (009/008 resolution).
- **FR-130**: Evidence types: `HTTP_TRANSACTION` (sanitized request metadata, status, header *names*, flagged values, body shape), `SECURITY_CHECK_RESULT`, `API_SURFACE`, `AUTH_STATE_TRANSITION`, `PERMISSION_COMPARISON`, `CLEANUP_RECORD`, `ADVISORY_MATCH`; 009 `SECURITY_REPRODUCTION` is reserved for the minimal reproduction record attached to a `CONFIRMED` finding (redacted, request template + observed outcome class), never a working exploit.
- **FR-131**: Evidence MUST NOT include raw credentials, session tokens, full sensitive bodies, customer records or unredacted secrets. A secret found in a response is evidence of *exposure*: recorded as `{kind, location, lengthClass}` only (an indicator containing no value, prefix, suffix or hash).
- **FR-132**: URL query redaction, PII minimization (no emails/phones/IDs stored; classes + counts), log sanitization (Sentry scrubbing extended to value-aware matching), artifact retention = report retention parity, tenant-isolated storage keys (`artifacts/<scanId>/<executionUnitId>/…`).
- **FR-133**: Screenshots/HAR/traces are NOT pixel/content-redacted (010 FR-046); 012 MUST NOT capture screenshots or HAR of authenticated pages in v1 (authenticated browser unsupported), and any report using 010 screenshots must not imply privacy review.
- **FR-134**: All customer-supplied responses are untrusted data: never interpreted as instructions (AI prompt-injection defense inherited from 011 FR-129 pattern), never rendered as HTML in the product UI, never fed to AI unredacted. Every stored target-controlled string (header/cookie/JSON-key names, banners, locations) passes a charset allow-list, a 128-character maximum and control-character stripping; UI and CSV exports escape.
- **FR-135**: Every evidence write is idempotent: it first claims `IdempotentClaim{scope:"sec-evidence-write", claimKey:"${scanPlanId}:${executionUnitId}:${attempt}:${kind}:${naturalKey}"}`.

### O — Findings, Severity, Coverage

- **FR-136**: **Finding confidence** (stored in `SECURITY_CHECK_RESULT` and displayed; not an `Issue` column) is one of: `CONFIRMED_VULNERABILITY`, `LIKELY_VULNERABILITY` (evidence-backed), `CONFIGURATION_RISK`, `INFORMATIONAL`. **Non-finding verdicts**: `NO_ISSUE_DETECTED`, `INCONCLUSIVE`, `NOT_TESTED`, `BLOCKED`, `UNSUPPORTED`. The mapping to 010's six verdicts is: `NO_ISSUE_DETECTED`≙`PASS`, the four confidence values≙`FINDING`, the rest identical. 012 uses its own kind/scope strings (011's approach) and does not widen 010's `CHECK_RESULT`.
- **FR-137**: `NO_ISSUE_DETECTED` MUST always be rendered with the statement of what was executed ("no issue detected by N executed probes of check X vN against E endpoints/I identities") and MUST NEVER be rendered as "secure", "passed security" or a bare PASS.
- **FR-138**: Confidence and severity are separate. Severity is derived by a deterministic table from `(check default severity, confidence, environment, exploit prerequisites, asset criticality hint)`; `LIKELY` never exceeds HIGH; `CONFIGURATION_RISK` never exceeds the check's cap (≤ HIGH; MEDIUM for most); `INFORMATIONAL` is `INFO`. CVSS vectors are included only when every base metric is determinable from evidence; otherwise omitted (never invented); CWE and OWASP-category tags are static per check; "business impact" and "asset criticality" are not inferred by Fahes.
- **FR-139**: Only `CONFIRMED`, `LIKELY`, `CONFIGURATION_RISK` and `INFORMATIONAL` verdicts call 009 `materializeFinding`; `INCONCLUSIVE`, `NOT_TESTED`, `BLOCKED`, `UNSUPPORTED`, `NO_ISSUE_DETECTED` appear only in coverage. A weak signal is never materialized above `LIKELY`; a high-severity hypothesis is never `CONFIRMED`.
- **FR-140**: `CONFIRMED_VULNERABILITY` requires a check whose registry entry declares `confirmable: true` **and** an oracle that observed fixture-confined, customer-registered proof (e.g. marker of another identity's fixture returned/modified) — never inferred from status code alone, never from AI. The fixture marker is a unique synthetic value of at least 16 characters, registered with the exact-value registry and absent from the actor's own resources; `CONFIRMED` requires the marker present for the actor **and** absent in the actor's negative-control read for the pair.
- **FR-141**: Fingerprints: `fingerprintParts = [checkVersionMajor, normalizedPathTemplate(apiIdentity), METHOD, identityRole?, parameterName?, probeFamily]` (009's `fingerprintOf` already hashes the `checkId` it is given, so it is not repeated in the parts); no line numbers, timestamps, tokens or response values; two checks that observe the same root cause on the same endpoint declare a shared `rootCauseGroup` and **every check in the group passes the group's canonical `checkId`** to `fingerprintOf`, so one Finding is produced (dedupe; cross-domain `rootCauseKey` is SPEC 014's). Materialization of a `rootCauseGroup` is a **group barrier**: members record their `SECURITY_CHECK_RESULT` as they resolve but do not call `materializeFinding` individually; the registered finalizer/sweep materializes the group's Finding **once**, after every member resolved, with the winner chosen deterministically before the call — highest confidence rank, then highest severity, then lexicographically first `checkId` — and `IssueEvidenceLink` rows for all supporting evidence; losing members carry `mergedInto`. This does not depend on update-on-conflict (009 materialization is first-writer-wins, `skipDuplicates`). **The barrier is defined over the plan's *scheduled* members only**: a REVERIFY plan, or any plan that schedules a subset of a group, defines the group as the scheduled members; unscheduled members neither block nor contribute; REVERIFY updates the existing Issue state through 009 and materializes no new Issue. Legacy and 012 findings for the same root cause are both visible during the parallel run and are not suppressed; duplicates end when the legacy checks are retired under the migration plan.
- **FR-142**: **Product security score is separate from vulnerability severity**: 012 changes no scoring weights; INFO and non-finding verdicts do not score. The SECURITY module result state (via the registered module-result finalizer) is `COMPLETE` only if every *applicable* requested check produced `NO_ISSUE_DETECTED`/finding verdicts; `DEGRADED` if any applicable check is `NOT_TESTED|BLOCKED|UNSUPPORTED|INCONCLUSIVE`; `NOT_APPLICABLE` (score `null`, excluded from the overall mean) if no check produced a real result. 012 adds **no new `ModuleState`**; the existing `FAILED` state (a valid `ModuleState`, verified) is written only when the finalizer or evaluator itself fails with a platform defect and no results (score `null`, `coverageComplete` `false`); if even that write fails, the marker stays `null` and every consumer treats it as incomplete (FR-186, FR-196). **Existing scoring treats `DEGRADED` as a scored, delivered state** (`MODULE_STATES_SCORED`; a scorable state with a null score is an upstream bug), so a `DEGRADED` SECURITY result carries a score computed from its findings **plus a mandatory, persisted `coverageComplete: false` marker (FR-186) and the `securityCoverageSummary`**; no consumer (report, certificate, SPEC 014 readiness) may present a `DEGRADED` SECURITY score as complete or as a security pass. **PRODUCT DECISION P13 — OWNER-APPROVED 2026-10-11**: uncapped `DEGRADED` scoring is rejected as a readiness PASS; the observed evidence-backed score is preserved and shown with the marker; readiness, certificates, reports, exports, notifications and badges are gated by FR-188.
- **FR-143**: Coverage (`securityCoverageSummary(scanPlanId)`, a pure read) reports facts: endpoints discovered / authorized / tested / skipped(+reasons); authentication states exercised; roles/identities tested; resource-ownership pairs tested; workflow steps executed; probe families executed; blocked / unsupported checks; cleanup outcomes. It distinguishes: no issue detected in executed checks; no checks executed; insufficient permissions; missing credentials; unsupported target; inconclusive response; incomplete scan. Absence of findings is never PASS.
- **FR-144**: AI may only explain/prioritize *after* deterministic verdicts are committed, through `ai-executor` with redacted inputs; AI never decides a verdict, confidence, severity, scope, authorization or whether a probe runs; AI-written text is labeled `AI_JUDGMENT` and cannot upgrade a verdict; AI never receives credentials, tokens, cookies, response bodies or fixture identifiers beyond redacted classes. The AI input assembler accepts only a closed schema of enums and numbers (never free strings from evidence), enforced by type and by test.
- **FR-145**: Findings carry `Issue.location` = canonical `METHOD + https://host/path-template` so reverify's F01 destination (`Issue.location`) is precise (009 risk #2).

### P — Security Check Registry and Idempotency

- **FR-146**: A versioned, vendored **Security Check Registry** (code-level, not a table; Principle II) holds `SecurityCheckDefinition` records (fields in FR-009 plus `id` (`sec.*`/`auth.*`/`authz.*`/`api.*`/`logic.*`/`dep.*`), `version`, `category`, `severityGuidance`, `classification`, `executionClass`, `targetApplicability`, `inputSchema`, `probeDefinition`, `requestBudget`, `timeoutMs`, `evidenceRequirements`, `coverageBehavior`, `reverifyBehavior`, `confirmable`, `idempotent`, `sideEffects[]`, `rootCauseGroup`, CWE/OWASP tags).
- **FR-147**: Parent-side check evaluation follows the 010/011 registry pattern: `onSecurityEvidenceCommitted` is the only call path producing `SECURITY_CHECK_RESULT`; claim `IdempotentClaim{scope:"sec-check-execution", claimKey:"${scanPlanId}:${check.id}:${check.version}:${scopeKey}"}` **before** the readiness query; `SECURITY_CHECK_RESULT` is excluded from the trigger set (non-recursion); `evaluate` is pure/synchronous over committed Evidence; `sweepUnresolvedSecurityChecks` is registered as a 009 module-result finalizer and records `BLOCKED`/`NOT_TESTED` for every registered applicable check with no result.
- **FR-148**: Active probes are executed by engine units (not parent-side); their **execution identity** is `(planId, checkId, checkVersion, endpointIdentity, identityRef?, probeIndex)`; the unit-level `idempotencyKey` is derived per 009 rule 4; per-probe execution claims (`sec-probe-attempt`) prevent a recovered unit from re-sending a probe whose `SENT` intent is already recorded.
- **FR-149**: Adding a check requires zero edit to dispatch code; the registry loader rejects: a declared class ≠ computed class, a probe whose destination isn't parameterized from authorized inputs, a missing `abortConditions`, a mutating probe without cleanup, a check with `confirmable: true` lacking an oracle, and any `requiredEvidenceKinds` containing `SECURITY_CHECK_RESULT`.
- **FR-150**: Check definitions are immutable per `(id, version)`; a changed probe is a new version; fingerprints include only the major version so a patch does not reopen findings.

### Q — Reverify

- **FR-151**: Security reverify uses 009 `resolvePlan(kind: REVERIFY)`: a new minimal single-unit plan; fresh F01 authorization with `destination = Issue.location`; fresh F07 admission; fresh credential lease via the broker (revalidating existence, expiry, revocation, version); fresh evidence; mutation budgets re-applied; previous findings and evidence preserved and linked, never overwritten.
- **FR-152**: Reverify supports: security-header, TLS-visible, cookie, auth-session, authorization, API-validation, business-logic and dependency-advisory findings via each check's `reverifyBehavior` (`FRESH_MINIMAL_PLAN`); it re-runs the single probe family needed, never a stored exploit; mutating reverify requires current consent and a fresh fixture state check.
- **FR-153**: Reverify outcomes: `PASSED` (executed probe observed the expected secure behavior), `FAILED` (issue observed again), `INCONCLUSIVE` (credentials expired/revoked, fixture missing, grant expired, environment changed, budget exhausted, endpoint gone — each with a closed reason); a reverify that could not execute is never `PASSED`.
- **FR-154**: A reverify refused by F01/F07 returns the upstream reason verbatim; no silent fallback to the old plan or credentials; the existing `webaudit-reverify` single-capability runner remains unchanged for today's passive capabilities.

### S — Reconciliation additions (lead rulings after contract drafting; see reconciliation-log.md)

- **FR-161** (dual-class rule): A request that carries a credential **and** is crafted (a `NEGATIVE_PROBE` such as a cross-identity authorization probe or a validation-boundary probe on an authenticated operation) is executed by an E14 unit (`ACTIVE_SECURITY`) with its own broker lease and `SessionHost`, and **every such request is checkpointed twice**: the primary `safetyCheckpoint(ACTIVE_SECURITY, consumes{request:true})` and a secondary class-qualified check for `AUTHENTICATED_WORKFLOW` with `consumes{request:false, concurrency:false}`; either `STOP` aborts. The grant (one grant listing both classes, or two grants — the customer's choice, 007 FR-006) MUST authorize both. Credentialed requests with no crafted element (login, logout, refresh, same-identity reads and workflow steps) are E15 `AUTHENTICATED_WORKFLOW` requests with a single checkpoint; a cross-identity replay is always a `NEGATIVE_PROBE` and therefore E14 dual-class (one definition of "crafted" for credentialed requests). Plan resolution (009) checks only the unit's primary class; the secondary class refusal therefore surfaces at dispatch as `BLOCKED` (recorded as upstream amendment AR-10 RECOMMENDED: allow per-unit additional authorization classes).
- **FR-162** (residual manifest): `CLEANUP_RECORD` residual manifests, and `SESSION_UNCONFIRMED` records, for units that were stopped, killed, cancelled or expired are written by the **parent-side SECURITY module-result finalizer / sweeper** from durable `MutationIntent` rows. This write is *parent-derived evidence, not unit-produced evidence*, and is therefore not subject to the unit fence (009 U-1) — but it is idempotent (`sec-evidence-write` claim) and never sends a request.
- **FR-163** (location binding): `Issue.location` is the canonical `METHOD https://host/path-template` string. Reverify parses it (`parseSecurityLocation`) and binds a **concrete destination** `{host, path, scheme, port}` (method ignored — F01 destinations carry no method) from the finding's recorded fixture/declared example; a location that cannot be bound to a concrete in-scope destination yields reverify `INCONCLUSIVE` / `SEC_REVERIFY_UNVERIFIABLE`; it is never guessed.
- **FR-164** (reverify routing): Legacy `resolveReverifyCapability` returns null for unknown namespaces (which silently becomes `UNVERIFIABLE`). 012 check namespaces `sec`, `auth`, `authz`, `api`, `logic`, `dep` MUST be routed to the 009 REVERIFY plan path **before** the legacy resolver; the legacy runner remains for legacy passive capabilities only. Reverify outcome `INCONCLUSIVE` maps to the existing Issue state `UNVERIFIABLE` (Issue state machine unchanged).
- **FR-165** (AI boundary in the SECURITY module): the SECURITY module's AI layer MUST be restricted to explanation/prioritization of committed verdicts; it MUST NOT emit findings: for `ModuleType.SECURITY` any `layer:'AI'` finding is dropped regardless of `checkId`, and AI explanation text is validated against the committed verdict and replaced by a static template on any mismatch.
- **FR-166** (claim staleness): an `IdempotentClaim` with no `resultRef` older than the owning unit's `timeoutPolicyMs + hardStopMarginMs` is stale and re-claimable only by a conditional `UPDATE`; stale-claim recovery never re-sends a probe whose durable intent is `SENT` or later.
- **FR-167** (account deletion): deleting a user account MUST crypto-shred every `CredentialVersion` of that tenant, revoke leases, and purge all 012 tenant tables (012 tables have no `User` relation by the zero-relation rule, so the existing `User` cascade does not reach them) and remove the tenant id from every `WorkerPrincipal.servedTenantIds`; the purge is an explicit, audited step.
- **FR-168** (API description storage): customer-provided OpenAPI documents are stored in an `ApiDescriptionDocument` record (tenant-owned, bound to a Target, content-digest keyed, R2 key `api-descriptions/<userId>/<targetId>/<digest>`), **not** as a 009 `Artifact` (which requires a scan and unit); `AdvisorySnapshot` payloads likewise use a platform-global key `advisory-snapshots/<digest>`. These are the only two non-scan stores; they reuse the existing R2 client, retention sweep and tenant-key checks and are **not** a second pipeline for scan evidence.
- **FR-169** (reverify billing): REVERIFY plans follow the existing `REVERIFY_COST` semantics (charge at resolution; refund for platform failure or refusal before execution) until F06 defines pricing — **PRODUCT DECISION P14 — PROVISIONAL**; whether a customer-side `INCONCLUSIVE` (expired credential, missing fixture) is refunded is an owner decision.
- **FR-170** (advisory freshness anchor): the advisory freshness bound is measured from the snapshot's `sourceRetrievedAt` (when the upstream advisory data was obtained), not its `importedAt`; freshness is further bounded by the newest advisory `modified` timestamp inside the payload (a re-stamped old export does not become fresh), and a signature is mandatory.
- **FR-171** (user cancellation and residue): because user cancellation is an F07 stop (`USER_CANCELLATION`), no cleanup request is ever attempted after a cancel (FR-122); the UI/report MUST state before a customer cancels a scan that has mutated fixtures that residual fixture state may remain (U30 dependency).

### T — Adversarial-review repairs (independent review, 2026-10-11; see adversarial-review.md §Disposition)

- **FR-172** (verified address binding — N2-1; supersedes the earlier B-1 text): for `ACTIVE_SECURITY`/`AUTHENTICATED_WORKFLOW`, every destination hostname MUST pass a *Verified Address Binding* (VAB) before plan resolution and again at dispatch. VAB establishes **control of the serving address and of the hostname's content at that address; it does NOT establish ownership of an upstream origin behind that address** (see FR-197). (a) *Preconditions*: the Target is verified by the HTTP-file method (`TargetVerification.method = FILE`); a DNS-TXT-only Target is refused (`SEC_TARGET_ADDRESS_UNVERIFIED`). (b) *Proof traffic* is **ownership-verification traffic, not security probes**: a fixed `GET` of the verification path, no credentials, no headers beyond `Host`, sent by a dedicated `AddressProofClient` on safe-net in the parent/API (never by the engine child). It is **not an F01 destination and not an F07 request unit**; it is never sent before the dispatch checkpoint has passed (grant and kill-switch checks precede it), is rate-limited per hostname (`level1RateBound`), is bounded locally (at most 2 x candidates + 8 re-proofs per unit), observes the kill switch at the <= 5 s liveness cadence, and is audited (`address_proof.run`). (c) *Enumeration*: candidates are the A/AAAA records resolved by safe-net at proof time; **more than 4 candidates, or any candidate safe-net classifies as non-public, refuses the hostname — never truncated, never a partial set**; every candidate must pass both proofs. (d) *Hostname proof, TLS targets*: connect to the candidate IP directly (no DNS), TLS >= 1.2, **SNI = hostname, ALPN `http/1.1` only, full certificate-chain, expiry and hostname validation against the system trust store, never relaxed**; `GET` the verification path with `Host: <hostname>`, no redirects, status 200, token match; record the leaf **SPKI hash**. A certificate that fails validation (self-signed, private CA, expired, wrong name) refuses the hostname (`SEC_TARGET_TLS_UNVERIFIED`): private-CA/self-signed staging is **unsupported in v1** (a pinned-certificate option is pending decision P18). **Plain-HTTP targets are unsupported for active and authenticated testing in v1** (class `PLAINTEXT_TARGET`, `SEC_UNSUPPORTED_TARGET_TYPE`): both proofs would be unauthenticated and credentials would cross cleartext. Only the default ports (80 for the address-control proof, 443 for the target) are supported: a destination on any other port is refused (class `NON_DEFAULT_PORT`, `SEC_UNSUPPORTED_TARGET_TYPE`), because the port-80 proof says nothing about a service on another port; every proof and every pin is bound to `(hostname, port)`. (e) *Address-control proof*: for every candidate, **plain HTTP on port 80 only**: `GET http://<ip>/<verification path>` with `Host: <ip>` (IPv6 bracketed), no redirects, status 200, token match. The proof request carries a fresh random query value and `Cache-Control: no-cache`; a response with an `Age` header greater than 0, a cache-hit indicator or a status other than 200 is refused (this narrows cache replay of a stale proof; the token itself is the tenant's public verification token, so the channel proves only that the address's default virtual host serves the tenant's file). This is a deliberate *separate* proof request and not a downgrade of probe traffic (probes keep the Target's scheme and full TLS validation). TLS cannot authenticate an IP literal, so this channel is unauthenticated: its exposure to an on-path injector is a **stated limitation**, mitigated by the TLS-authenticated hostname proof, the SPKI pin and periodic re-proof. A destination that cannot answer on port 80 with the file at the default virtual host (HTTPS-only, HTTP-to-HTTPS redirect, port 80 closed) **fails the address-control proof and is refused for active testing (class `NO_DEFAULT_VHOST`)**; that product impact is accepted. (f) *Pinning*: the unit's connect guard is pinned to the `provenAddressSet` for the unit's whole life — fresh DNS is never consulted after the proof, any other peer address is refused, and **every upstream connection (one per request, FR-199)** must present the recorded SPKI hash (TLS targets) or is refused; the address-control proof is re-run for every pinned address at unit start, at least every 5 minutes, and on any SPKI mismatch, connection failure or certificate change; a re-proof failure ends the check `BLOCKED` (`SEC_TARGET_ADDRESS_UNVERIFIED`) and stops the unit's requests. A DNS change between authorization and connect therefore cannot redirect probes, and if the pinned addresses stop answering the unit fails closed and never falls back to new DNS results. (g) *Plan time*: no network proof; a `PROVEN` `TargetAddressProof` for the hostname no older than 24 h (recording `addressSetHash`, `destinationClass`, SPKI hash) is required, else refusal; dispatch re-proves fresh and creates the pin. Wildcard scopes prove each hostname individually; IP-literal destinations are never in scope (the proof requests are the only IP-literal traffic and are not scope destinations). (h) *Destination classes*: `DIRECT_PROVEN` (passed (a)-(e)) is the only class eligible for active classes, and only under the Destination Authorization Policy (FR-197). `DNS_TXT_ONLY`, `PLAINTEXT_TARGET`, `NON_DEFAULT_PORT`, `SHARED_OR_EDGE` (hostname proof passes, address-control fails: shared hosting, CDN, PaaS, anycast edge, load balancer without a default-vhost token), `TLS_UNVERIFIED`, `NO_DEFAULT_VHOST`, `TOO_MANY_ADDRESSES` and `NON_PUBLIC_ADDRESS` are **UNSUPPORTED for active/authenticated testing and refused**; passive observations are unaffected. (i) *Fail closed*: any proof error, timeout, rate-limit refusal, mismatch or unlisted condition => `SEC_TARGET_ADDRESS_UNVERIFIED` (or `SEC_TARGET_TLS_UNVERIFIED` for certificate failures) and zero probe bytes. The earlier customer-declared expected-address set and shared-edge attestation are **removed**; the customer may only narrow the proven set (`allowedSubset`).
- **FR-173** (signing authority, broker trust anchor and anomaly rules — B-2, N2-7, N5-7, N5-8): the **Plan Resolver, which 009 places in `apps/api` (`apps/api/src/services/planning/`), is the sole signing authority**. At plan resolution it stamps each credentialed unit with `configuration.x012.unitMac`, an HMAC-SHA-256 under the versioned `unitMacKey` over the canonical encoding of `(unitId, scanPlanId, userId, targetId, credentialBindingRef, grantIds, executionUnitClass, identityRefs, configurationDigest, inputsRootDigest, platformEpoch, keyVersion)`; editing `identityRefs`, class or configuration invalidates the stamp. The key is held only by the API plan-resolution principal and the broker's verifier; **no signing or verification key exists in any worker process, environment or image** (test `worker.no-mac-key`). The broker verifies the stamp on every issue; absent/invalid stamp, unavailable key or unknown key version => `SEC_BROKER_DENIED` (fail closed). The broker reads the grant (`TargetAuthorization`), plan, scan, kill-switch and credential rows itself through its own DB role and treats an `AdmissionLease` as a liveness fence only, never as authority. **Anomaly detection is keyed per authenticated worker principal across all tenants, per tenant within a principal, and per tenant across all principals.** A *worker principal* is the identity the broker authenticates from the connection itself — a per-instance mTLS or workload identity, and in the database a per-instance login role registered in `WorkerPrincipal` (FR-201); **`principalId` and `hostInstanceId` are derived by the broker and by the privileged database functions from that authenticated identity and are never accepted as a caller argument** (`hostInstanceId` is the principal's identity; one live host instance per principal; a pool-shared credential fails SG3). Rules (**every threshold, window and count below is an unmeasured design starting value, not a calibrated one**: T523 must derive them from measured worker concurrency and the SG3 activation record must cite that calibration; until then they are not claimed to fit production): R1 more than 5 distinct tenants with issues from one principal in 10 min; R2 more than 20 distinct credential references from one principal in 10 min; R3 more than 30 issues per minute from one principal; R4 an issue for a unit whose `UnitDispatchRecord.principalId` is not the authenticated principal; R5 an issue for a unit created after its plan's `resolvedAt`; R6 an **integrity-deny** ratio above 50 % over 5 min **evaluated only when the window holds at least 10 events (issues plus integrity denials)**, counting only integrity denials (stamp/MAC failure, unit-state or claim mismatch, R4/R5 violations, R1-R3 anomaly denials; never an R7 quota denial) and never denials a tenant can cause (credential revoked/disabled/expired, consent or enablement missing, lease busy, identity suspect, attempt limits, grant revoked); **CS1 (claim spread)**: when one principal's `UnitDispatchRecord` rows span more than 5 distinct tenants in 10 minutes (a starting value, uncalibrated, T523), `sec_claim_unit_host` denies the claim (`CLAIM_DENIED(CLAIM_SPREAD)`), the denial is a breach that advances the streak, and a quarantined principal cannot claim; a principal registered with `servedTenantIds` is also refused every other tenant's unit (`CLAIM_DENIED(TENANT_NOT_SERVED)`); R7 is a **tenant quota, not evidence of principal misbehavior**: more than 5 distinct references for one tenant from one principal in 10 min, or more than 8 distinct references for that tenant across **all** principals in 10 min, denies the issue (`SEC_BROKER_DENIED`, detail `TENANT_QUOTA`, audit `broker.tenant_quota.deny`) and is **not** an integrity denial, **not** a breach, never changes `breachStreak` or `lastBreachBucket`, is never counted in R6 and never quarantines a principal; it is evaluated from `ISSUE` events only and a quota denial writes no event, so it cannot inflate R1-R3; because R7 caps one tenant at 5 distinct references per principal, one tenant alone cannot reach R2 (20 references) or R1 (more than 5 tenants) on a principal, while a sustained single-tenant burst above R3's 30 issues per minute on one principal can still breach R3 and, after three consecutive buckets, quarantine that principal for every tenant (a stated availability residual, bounded by queue concurrency and cleared by the operator). **Enforcement is atomic across broker replicas**: every issue, and every integrity denial, runs in a transaction that first takes `SELECT ... FOR UPDATE` on the principal's `BrokerPrincipalState` row, then (lock order is always principal, then tenant — never the reverse) a transaction-scoped advisory lock on the tenant, then reads the windows from `BrokerPrincipalIssueEvent`, evaluates R1-R7 and inserts the event in the same transaction; concurrent issues serialize, two replicas cannot both pass the same window, and `SERIALIZABLE` isolation is an acceptable equivalent only with the same lock order; a deadlock or serialization failure retries and never grants. Events are idempotent on a unique key (`(principalId, leaseKey)` for issues, `(principalId, unitId, attempt, reasonCode)` for denials), so a retry or a replayed request is not counted twice; integrity denials are recorded by a second short transaction that takes the same locks in the same order after the issue transaction rolled back. Response: deny the issue and alert (audit `broker.anomaly.deny`). **Quarantine uses durable counters**: a *breach* is an anomaly denial under R1, R2 or R3, a CS1 claim-spread denial, an R4/R5 denial, or an R6 trip (never an R7 quota denial); a *breach window* is a tumbling 10-minute bucket `floor(epoch seconds / 600)`; `BrokerPrincipalState.breachStreak` and `lastBreachBucket` are updated inside the principal-row-locked transaction (a breach in bucket b: unchanged if `lastBreachBucket = b`, `breachStreak + 1` if `lastBreachBucket = b - 1`, otherwise `breachStreak = 1`; then `lastBreachBucket = b`); `breachStreak` of 3 sets `quarantinedAt` (`broker.principal.quarantine`), after which **all** the principal's issues and claims are denied (fail closed) until an operator `clearPrincipal` (audited, which also resets the streak). Because the streak lives in the row, a restart or another replica neither resets nor fragments it. Legitimate bursts (deploy, backlog drain) are bounded by queue concurrency and cleared by the operator. **MAC validation is not the complete trust boundary**: the database privilege isolation of FR-201 (AR-13, REQUIRED before broker or active-engine activation) is a mandatory prerequisite. **Accurate residual (true only when FR-201 is enforced)**: a compromised worker instance, acting only as its own authenticated principal, can claim through `sec_claim_unit_host` **any live non-terminal unit of any tenant whose class is in that principal's registered `servedClasses`** (the claim is class-scoped by the function, which refuses other classes, and is **not tenant-scoped**: the queue is a routing convenience, not a database control), drive it through the guarded edges, and then obtain a lease for it — at most at the R1-R3 rates (5 tenants and 20 references per 10 minutes, 30 issues per minute), capped per tenant across all principals by R7, each lease lasting at most min(unit remaining time, 30 minutes); for a lease's life it holds that tenant's credential secret in memory and can exfiltrate it or use it directly against the target; N compromised instances multiply the rates by N until each is quarantined; it cannot obtain leases for terminal, historical, already-leased, units of a class outside its `servedClasses`, or other-principal units, cannot impersonate another principal, and can deny service by claiming units without running them (they then time out). Through the claim it can also finalize those units: refuse them with a closed, host-asserted reason, or after driving them to `RUNNING` complete or fail them, and so block their direct dependents; falsified outcomes are limited to units it claimed. Without a claim it can refuse only `PLANNED` units of its served classes, only for the four database-verified step-0 reasons (`sec_refuse_unclaimed_unit`, FR-201(c)(ii)), which adds no power beyond what the database already holds true; it cannot call the sweep, finalize another class, a terminal unit, another principal's claim or any unit outside `servedClasses`. The refusal and sweep paths therefore do not widen the tenant blast radius, which is already every tenant's live units of the served classes through the claim. The same claim-owner binding applies to every other worker-callable broker operation (reserve, mark, resolve, release, status, confirm), so none can be aimed at another tenant's identity or lease (MA-01). **Residual after the confinement of FR-201(j) (MA-07)**: (1) a compromised worker principal can still claim any live unit of its served classes (only its `servedTenantIds` when registered with them); once it holds a claim it can read that unit's tenant context and manifest members, write that unit's evidence, mutation intents, claims and progress, drive and finalize it, and obtain its credential lease; it can no longer write, squat or read anything of a unit it has not claimed, read another tenant's configuration or fixtures, call 008 admission for another tenant, or forge check results, findings or module results (written only by `fahes_sec_derive`); (2) under a shared pool the number of tenants it can reach per window is bounded by CS1, **not eliminated, so tenant isolation under worker compromise is not achieved**; it is achieved only for principals registered with `servedTenantIds` and routed to those tenants' jobs (Mode S, OD-4, AR-20); (3) units of other execution classes and the legacy SECURITY capabilities keep today's unconfined worker writes (AR-21), so evidence they produce is an input a compromised passive worker can poison, and reports state the producing unit class; (3b) the object store is outside the database: artifact uploads use grants from `sec_register_artifact` or a prefix-scoped credential (T862); (4) **evidence integrity is not provided (IC-3)**: claim-scoped access prevents cross-unit contamination; it does not prove that the evidence a compromised claimant writes for its own claimed unit is true. Such a worker can fabricate `HTTP_TRANSACTION`, `PERMISSION_COMPARISON` and `AUTH_STATE_TRANSITION` content, including the child-evaluated oracle booleans, so the parent-derived results (`fahes_sec_derive`) can be a false `NO_ISSUE_DETECTED`, a false `LIKELY_VULNERABILITY` or `CONFIRMED_VULNERABILITY`, or a false `BLOCKED` for the units it claimed (in a shared pool, for any tenant it can claim, bounded by CS1; in Mode S, only for the tenants it serves). The derived layer enforces provenance (unit, class, evidence kind, check membership, fence) and non-recursion, not truthfulness. Mitigations that exist: the closed harmless alphabet and the verdict caps (a `LIKELY` ceiling for engine-evaluated verdicts, `CONFIRMED` only for a `confirmable` check with a fixture-confined oracle), `requiresProducerCompleted`, redaction, a fresh-unit reverify, the per-tenant allowlist and the SG10 review; no independent attestation of target responses exists in v1, and reports, coverage summaries, exports and readiness consumers must say that results rest on worker-reported evidence (FR-137, FR-188). SG10 must record this limitation as accepted before activation. Without FR-201 the residual is unbounded and activation is refused.
- **FR-174** (HostileTextExecutor — B-4): all processing of target-controlled text — redaction, every classifier (CSP, Set-Cookie, reflection, engine-error signature, PII, name classifiers), JSON shaping and OpenAPI parsing — MUST run inside a **HostileTextExecutor**: a pool of `worker_threads` with `resourceLimits`, a per-job input cap (<= the read cap), and a per-job hard timeout (provisional 200 ms; 10 s for OpenAPI) after which the thread is **terminated**, not merely reported — in both the engine child and the parent; no main thread ever runs a pattern over hostile text. A terminated or failed job fails closed: redaction => `{"_redactionFailed": true}`; a classifier => `INCONCLUSIVE`/`SEC_ANALYSIS_BUDGET_EXHAUSTED`. Linear-time patterns are additionally required (defense in depth) and event-loop lag stays under 100 ms in an adversarial-complexity test for **every** classifier, not only redaction. A same-thread timer that merely reports an overrun does not satisfy this requirement.
- **FR-175** (child confinement and one-time admission permits — B-5, N2-3): the engine child has **no network path**: OS/container egress is denied (verified at SG7; if it cannot be enforced the authenticated/active flags refuse to enable), stdio is ignored (FR-194), and its only channel is the parent IPC. A request reaches the network only if the parent admitted a request frame (FR-190). Admission yields a **single-use permit that is internal to the parent** — in-memory, bound to `(executionUnitId, requestOrdinal, stepId, host:port, request-digest, expiry <= 10 s)` and consumed atomically when the gate opens the one upstream connection. **The permit is parent-internal bookkeeping and defense in depth against a parent defect, not a security boundary against the child**: the child never holds or presents a permit, and the control that stops a compromised child is that it can only name a plan step (FR-200) and that the admission ledger allows each ordinal to be sent at most once. A replayed ordinal, or an expired or mismatched internal permit, => refusal `SEC_EGRESS_PERMIT_INVALID`. The request mechanics (structured frames, canonical serialization, TLS, connection lifecycle) are FR-199. A gate failure means no egress (fail closed); parent death removes egress; the child exits on IPC disconnect within 2 s or a missed parent heartbeat; the parent validates every child message against the unit configuration with a closed schema, never accepts proof fields (`jarDisposed`, `childExited`) from the child and observes process exit itself. **T650 is a mandatory implementation feasibility gate (before SG5), not a demonstrated fact**: planning closure does NOT imply that the structured-frame gate, per-request TLS handshakes at the unit's request ceiling, response streaming to the child's parser, OS-level egress denial on the chosen hosting, and the TLS-stack exposure decision (parent versus an isolated egress helper process) are feasible. - **FR-190** (admission order and fail-closed matrix — N2-4): the parent admits a request frame only after the following, **in this order**; every dependency that errors, times out or is unavailable => no admission and the closed reason shown. **Phase A — side-effect-free reads (no budget, ledger or counter changes)**: (A1) database clock (`SEC_SCOPE_GATE_ERROR`); (A2) `securityScopeGate` including the consent record, the `ActiveTestingEnablement` (FR-197), cool-off and environment reads (`SEC_SCOPE_GATE_ERROR`; missing or stale => `SEC_CONSENT_MISSING` / `SEC_DESTINATION_AUTHORIZATION_UNMET`); (A3) the exact-value registry loaded for every secret in play (`SEC_SCOPE_GATE_ERROR`); (A4) address pin intact and re-proof not overdue (`SEC_TARGET_ADDRESS_UNVERIFIED`); (A5) for credentialed requests a broker `getLeaseStatus` for this request (<= 1 s; `SEC_BROKER_UNAVAILABLE` or the lease reason) and the cached ledger health within its grace (FR-193; `SEC_BROKER_UNAVAILABLE`/`SEC_RESTORE_QUARANTINE`); (A6) the kill-switch pending-stop read (F07 `KILL_SWITCH_PENDING` verbatim). **Phase B — reservations, all releasable**: (B0) the `sec-probe-attempt` claim for this probe, releasable by its owner before C1 (a claim with no `resultRef` and no `SENT` mark is deleted on release; after C1 it is never released); (B1) for LOGIN/REFRESH, `reserveAuthAttempt` (state RESERVED, FR-191); (B2) local budget atomic `reserve` (`SEC_BUDGET_LOCAL_*`). **Phase C — the single irreversible step**: (C1) the F07 `safetyCheckpoint` consuming the request unit with the per-request key (F07 reasons verbatim; `INTERNAL_ERROR` => none). - **FR-197** (Destination Authorization Policy — N2-2; PRODUCT DECISION P16, PENDING owner approval; fail-closed default): address and hostname proofs (FR-172) show control of the serving front and of the hostname's content at that address. They **cannot show that the origin behind a front is owned by the tenant**: a tenant-controlled reverse proxy or forwarder can pass every proof (it can serve the proof paths itself and forward every other path) and relay probes to a third party's origin. This is a **security limitation that no technical proof in this specification closes**, so authorization for active/authenticated testing is established by an explicit policy, **not** by proof and **not** by customer attestation alone. Active or authenticated use of a destination requires ALL of: (1) VAB class `DIRECT_PROVEN` (FR-172); (2) a current `SecurityConsentRecord` carrying an explicit **origin-ownership warranty** — the customer warrants that the origin serving the hostname is owned or controlled by the customer, that no part of it forwards to a third party's origin, and accepts responsibility for third-party effects; a warranty creates accountability but is **not treated as proof**; (3) a current **`ActiveTestingEnablement`**: an operator-reviewed approval of the Target (evidence reviewed by a Fahes operator, bound to the Target and its hostnames, expiring in at most 90 days, revocable, audited) created only through an operator route; (4) the containment controls: identifying request headers on every probe (`User-Agent` containing `FahesSecurityScan/<id>` and `X-Fahes-Scan-Id`), published source IP ranges and an abuse contact, per-tenant active-request ceilings by account trust tier (a new tenant's ceiling is low until an operator raises it), and the tenant-scope kill switch on an abuse report. Until the owner approves the policy (P16) **and** the operator enablement process exists, active and authenticated execution is **refused for every destination** (`SEC_DESTINATION_AUTHORIZATION_UNMET`, gate SG8). A tenant-controlled forwarder remains *undetectable*: the policy's purpose is accountability and a bounded blast radius, not detection, and destinations whose origin independence the policy cannot support are refused rather than attested into scope.
- **FR-198** (execution-backed partial settlement — N2-6, F-08; PROPOSED policy P17, NOT approved, active only when `x012.settlementMode = CLASS_LEVEL`): applies only to scans created after the owner approves P17 **and** AR-17 (ADR-005 amendment). Settlement runs once per `ScanPlan` at the scan's terminal state (COMPLETED, FAILED, TIMED_OUT, CANCELLED). **Billable weight**: each registry check declares `billingWeight` (default 1; parent-synthesized sweep results weigh 0); `PASSIVE_SECURITY` also counts the legacy SECURITY capabilities (weight 1 each: `plannedWeight` = planned legacy capabilities, `executedWeight` = legacy `CapabilityExecution` rows with a delivered result), added to the 012 passive weights, so the whole of today's SECURITY price is covered. `executedWeight(class)` for 012 checks is the sum of weights of checks with a non-synthesized result whose verdict is `NO_ISSUE_DETECTED`, a finding verdict, or `INCONCLUSIVE` **with at least one admitted request or completed evaluation recorded**; `BLOCKED`, `NOT_TESTED`, `UNSUPPORTED`, refused, `INCONCLUSIVE` without executed work, and work lost to a platform failure (unit `FAILED`/killed by the platform, `ENGINE_DEFECT`) weigh 0 (this reproduces today's refund for undelivered work). **Price allocation**: the SECURITY area quote is split by the F06 class price table over `{PASSIVE_SECURITY, ACTIVE_SECURITY, AUTHENTICATED_WORKFLOW}` (interim: all of today's SECURITY price is `PASSIVE_SECURITY`; the other two are 0 and not offered). **Charge** per class = `floor(classPrice x executedWeight / plannedWeight)`; when `plannedWeight = 0` the class charge is 0 and its whole price is refunded (nothing applicable was planned); the full price is charged only when `executedWeight = plannedWeight`; **refund** = the sum of `classPrice - classCharge`, an integer by construction (rounding favors the customer). **Idempotency**: a `SecuritySettlement` row unique on `scanPlanId` anchors the settlement and its credit transaction; a replay finds the row and is a no-op; reverify is billed separately and never re-settles. **Precedence**: in this mode the SECURITY area is settled **only** by this function and is excluded from `refundForUndelivered`, which keeps its current semantics for every other area, for scans in `AREA_COUNT` mode and for scans without the requirement — no double refund; the existing platform-failure refund of the SECURITY area is replaced by the weight rules above. **Cancellation, timeout and failure**: executed weight is measured from committed results at the terminal transition; in-flight checks without a committed verdict weigh 0. **Retention**: `SecuritySettlement` is a financial-ledger companion record handled with the credit ledger's retention (FR-167). Billing integration has a single owner: the worker terminal path (`terminal-refund.ts`) calls `settleSecurityClasses` and `securityBillableWorkSummary` (read-only input).
- **FR-199** (canonical egress request protocol, TLS and connection lifecycle — N2-3): the child never emits HTTP bytes. `SecurityHttpClient` in the child sends the parent only a **step reference frame** over IPC (closed schema `{stepId, credentialSlots[]}`, FR-200); it names no method, URL, header or body. The parent renders the request from the immutable plan step and the validated slot values (body up to `maxRequestBytes`, default 64 KiB; no streaming request bodies in v1), admits it (FR-190), and **the gate serializes the HTTP/1.1 message itself**: it sets `Host` from the admitted host:port, sets `Content-Length` from the body length and always sends `Connection: close`. It **rejects** any `Content-Length`, `Transfer-Encoding`, `Connection`, `Host`, `Upgrade`, `Expect`, `TE`, `Trailer`, `Proxy-*`, `Keep-Alive` or `HTTP2-Settings` header (`SEC_EGRESS_PERMIT_INVALID`, detail `FORBIDDEN_HEADER`), header names outside the closed set of FR-066 plus the credential injection headers declared in `injectionSpec`, values containing CR, LF or NUL, more than 32 headers or 16 KiB of headers, methods outside GET/HEAD/POST/PUT/PATCH/DELETE/OPTIONS (no CONNECT or TRACE), URLs with userinfo or a fragment, and any host:port other than the admitted one; the gate does **not** normalize or decode the path: it sends the path bytes exactly as the parent rendered them (canaries are byte-exact), and **refuses** a rendered path containing dot-segments, backslashes or encoded ambiguity (`%2e`, `%2f`, `%5c`, double encoding) unless the step template declares it, and refuses any path whose scope outcome differs between the raw form and a single percent-decoded form (the origin's own decoding is unknown, so scope is evaluated on both and must agree). Because the gate generates all framing, request smuggling by length conflict, desync or pipelining is **not representable**. Policy: HTTP/1.1 only (ALPN `http/1.1`; an HTTP/2-only target is `UNSUPPORTED`, `SEC_UNSUPPORTED_TARGET_TYPE`); `Upgrade`, WebSocket and `Expect: 100-continue` are unsupported; **one request per upstream connection, no connection reuse**; TLS >= 1.2 with full chain, expiry and hostname validation and the recorded SPKI hash (FR-172f), session resumption disabled across units, and `rejectUnauthorized: false` never appears anywhere (a code-search test fails the build). Response handling: the gate streams **opaque response bytes** to the child under the response cap (header block <= 64 KiB; total <= read cap + 16 KiB) with connect 5 s, first-byte 15 s, **idle 5 s after the last received byte** and total 30 s timeouts, closes the upstream on the cap or a timeout (a server that ignores `Connection: close` therefore holds a request for at most the idle timeout once it stops sending; the duration budget accounts for the worst case per request and the cost is a T650 measurement), and **never parses or follows** a response; response framing is decided by the child inside the HostileTextExecutor, and a redirect is never a child decision: the parent follows it only through a planned `REDIRECT_HOP` step (FR-200(e)) as a **new admitted request that passes the full admission pipeline**. The gate runs in the **parent** process; the TLS client in the parent is hostile-certificate exposure inside a trusted process, and an isolated egress-helper process is an alternative that the T650 spike must evaluate.
- **FR-200** (parent-authoritative request authority — F-01, A1, A2, N5-1, N5-2, A1 residuals): the engine child is **untrusted for request semantics**. Every request is bound to an immutable, authorized plan step held by the parent. (a) *Signed inputs (A1)*: the steps are rendered only from **plan-time-immutable inputs** that are named in the unit's input manifest `configuration.x012.inputs` and covered by the unit MAC (FR-173). The manifest covers exactly: `API_SURFACE_ROW` (persisted evidence of an earlier derivation or scan, never evidence produced during this plan, FR-063), `API_DESCRIPTION_DOC` versions, `OPERATION_DECLARATION` versions (FR-192), `FIXTURE_RESOURCE`, `TEST_ROLE` and `TEST_IDENTITY` versions, `SECURITY_CONFIG_VERSION` and the `CHECK_REGISTRY` version. Each item is `{kind, ref, userId, targetId, version, contentDigest, sizeBytes}` with `contentDigest` = SHA-256 of the item's canonical bytes (raw stored bytes for a document, an object or a 009-owned Evidence content; RFC 8785 canonical JSON of exactly the columns listed for that kind in data-model 4.9L for a 012-owned row — columns not listed are runtime state re-read live by their own guard and are never plan authority); the manifest is `{schema:'x012.inputs.v1', items sorted by (kind, ref), rootDigest}` with `rootDigest` = SHA-256 of the canonical JSON of the sorted items, and `rootDigest` is part of the MAC tuple as `inputsRootDigest`. The Plan Resolver (API) computes the digests when it resolves the plan, refuses an item that belongs to another tenant or Target, is newer than the resolution time, or is older than the staleness limit (30 days, provisional), and refuses a plan above the item cap (2000 items). Before any parsing or rendering the worker parent loads each item by immutable reference, **recomputes the content digest over the raw bytes and compares it with the manifest before the bytes reach any parser** (parsing happens only in the HostileTextExecutor, FR-174), checks `userId`/`targetId`/scan binding, and recomputes `rootDigest`; a missing, substituted, mutated, stale or mismatched item, or a `rootDigest` that does not match the MAC-covered value, refuses the unit before the dispatch checkpoint with `SEC_SCOPE_GATE_ERROR` (audit `unit.inputs_mismatch`; zero F07 consumption). **The renderer receives only the verified items**: any read of a row, document or configuration outside the manifest for plan authority is a defect (test `engine.inputs.renderer-reads-only-manifest`: the renderer runs against a database stub that fails on any read, and a step that needs an unlisted input refuses the unit). `inputsRootDigest` is the MAC tuple's only input-related member and is the `rootDigest` above, nothing else. (b) *PlanStepTable*: the parent renders a table `{schema:'x012.steps.v1', unitId, attempt, scanPlanId, userId, targetId, inputsRootDigest, registryDigest, steps[], tableDigest}` with deterministic rendering (the same inputs always give the same `tableDigest`); the parent records `tableDigest` once through `sec_record_step_table` (FR-201: a second, different digest for the same `(unitId, attempt)` is refused, so a restart cannot change the authorized steps). Each step is `{stepId (deterministic from unitId, checkId, checkVersion, probeIndex, seq), seq, checkId, checkVersion, probeIndex, callSite, actionCategory, mutationClass|null, classification, identityRef|null, role|null, fixtureResourceId|null, destination{scheme:'https', host, port:443} (one of the proven destinations), operationRef{operationKey, declarationVersion|null} (required for every `REDIRECT_HOP` step and for every step with a path-position slot; it names an `OPERATION_DECLARATION` item of the manifest), method, pathTemplate, queryTemplate, headerTemplate, bodyTemplate, slots[], successors[stepId], redirect{allowedTargetStepIds[], maxHops}|null, maxExecutions, idempotent, expectedObservation, evidenceKinds}`; every slot is `{slotId, type, position{kind, name}, constraints{shape, charset, maxBytes, values[]}, source}` with **four independent axes**: `type` is the *origin class* of the value (`CANARY | FIXTURE_IDENTIFIER | CREDENTIAL | RESPONSE_DERIVED | HOP_MATCHED`); `position.kind` is *where* it is substituted (`HEADER | QUERY | BODY_FIELD | COOKIE | PATH_SEGMENT`, never a type); `constraints.shape` is *how it is validated* (`UUID | UINT | HEX | ENUM | TEXT`); and `source` is the provenance record the type requires (defined per type in (d)). (c) *Frame (N-6)*: the child sends only `{stepId, credentialSlots[]}`; **the ordinal is assigned by the parent at admission** (monotonic per unit, never child-supplied) and the child supplies no method, URL, header, body, category, identity, check id or authorization context; a frame with any other field is refused. The parent derives every authorization input of FR-190 from the step. (d) *Slots and provenance (A2)*: no value that influences the request is accepted on the child's say-so. `CANARY` is derived by the parent from `(planId, checkId, checkVersion, apiIdentity, parameterName, probeIndex)`; `FIXTURE_IDENTIFIER` is taken by the parent from the step (the identifiers come from the digest-covered `FIXTURE_RESOURCE` input); `CREDENTIAL` is the only slot type the child supplies, and the value must equal an exact-value-registered secret of **the step's** identity, where registry entries come only from the broker lease delivered to the parent or from a session value the **parent extracted** from the response of an admitted `LOGIN_ATTEMPT`/`SESSION_REFRESH` step by that step's declared extractor; `RESPONSE_DERIVED` is **extracted by the parent**, never supplied by the child: the slot declares `source{fromStepId, extractor{kind: JSON_POINTER|HEADER|SET_COOKIE|BOUNDED_CAPTURE, expr}, tokenClass (CSRF_TOKEN|SESSION_TOKEN|ANTI_REPLAY_NONCE, required), maxAgeMs (default 60 000, max 300 000), consumeLimit (default 1)}`; the parent keeps the bounded response bytes of each admitted step it relayed (a `ResponseRecord{stepId, ordinal, identityRef, destination, receivedAt, digest}`), runs the extractor in the HostileTextExecutor over the **retained bytes of the most recent completed execution of exactly `fromStepId`, for the same identity, destination and attempt**, applies the slot constraints and registers the value with the exact-value redactor. A value is refused if the record is missing, truncated, older than `maxAgeMs`, of another step, identity, destination or attempt, already consumed `consumeLimit` times, or extraction fails or violates the constraints; when provenance is unavailable the step is **not sent**, nothing is admitted or consumed, and the check ends `INCONCLUSIVE` (`SEC_RESPONSE_AMBIGUOUS`). For every slot, charset, length and position limits are defence in depth, not the control. **Path-position slots (N5-2)**: any slot whose `position.kind` is `PATH_SEGMENT`, whatever its type, must declare a closed typed `shape` — `UUID`, `UINT` (at most 18 digits), `HEX` (fixed length) or `ENUM` (a fixed value list inside the digest-covered step); the free `TEXT` shape (charset plus length) is refused for a path position when the table is rendered (the unit is refused `SEC_SCOPE_GATE_ERROR`, audit `unit.step_table_invalid`); a path-position value must also satisfy the operation rule of (e). **Authoritative source by slot type (L3)**: `CANARY` has no source object (the parent derives it); `FIXTURE_IDENTIFIER` has `source{fromInput: <FIXTURE_RESOURCE manifest ref>, identifierKey}` (a digest-covered input); `CREDENTIAL` is the only type taken from the frame (`credentialSlots[]`) and must equal an exact-value-registered secret of the step's identity; `RESPONSE_DERIVED` has `source{fromStepId, extractor, tokenClass, maxAgeMs, consumeLimit}` and is a **token slot only** (MA-02): `tokenClass` is one of `CSRF_TOKEN | SESSION_TOKEN | ANTI_REPLAY_NONCE`, the position is `HEADER`, `COOKIE`, `BODY_FIELD` or the check's declared token `QUERY` parameter, and a `RESPONSE_DERIVED` slot in a `PATH_SEGMENT` position, without a `tokenClass`, or whose value is used as an object identifier is refused when the table is rendered (`SEC_SCOPE_GATE_ERROR`, audit `unit.step_table_invalid`), because object identifiers come only from `FixtureResource.identifiers` (FR-092); `HOP_MATCHED` has `source{fromStepId (the originating step), part: PATH_SEGMENT index | QUERY_VALUE name}` and its value is cut **by the parent's byte-exact matcher** from the `Location` of the retained `ResponseRecord` of exactly that step, identity, destination and attempt (the same age, truncation and consume rules as `RESPONSE_DERIVED`); **a `HOP_MATCHED` slot always declares a closed `constraints.values[]` filled at render time from plan-known identifiers only (the digest-covered `FIXTURE_IDENTIFIER` values of the step's fixture, or the value the originating step itself used for the same position), and the matcher accepts a path segment or query value only if its bytes are a member of that list, so the target's `Location` can select only among identifiers the plan already authorized and can never introduce a new object identifier (MA-02, FR-092)**; it exists only inside a planned `REDIRECT_HOP` step, the frame schema has no field that can carry it, and a missing, truncated, stale, consumed, other-identity or other-destination record means the hop is not followed (fail closed, nothing admitted or consumed). `HOP_MATCHED` is not a `REDIRECT_LOCATION` slot: no slot type lets the child or any other component supply or choose a `Location`. **Query substitutions (L3)**: a query-position slot of a `REDIRECT_HOP` step is held to the same closed-shape rule as a path position (`UUID`, `UINT`, `HEX` or `ENUM`; `TEXT` is refused at render with `SEC_SCOPE_GATE_ERROR`, audit `unit.step_table_invalid`); free-`TEXT` query slots remain possible only for parent-derived values of ordinary steps (a canary), never for a value that comes from a response. (e) *Redirects and operation identity (A2, N5-1, N5-2)*: a redirect is never a child decision, there is no `REDIRECT_LOCATION` slot type, and no component other than the parent resolves a `Location`. The parent extracts `Location` from the retained response of the exact step and follows it **only** if it matches a planned `REDIRECT_HOP` step named in that step's `redirect.allowedTargetStepIds` (a planned hop has classification at most `C1`, method `GET` or `HEAD`, the same identity and destination origin, and `maxHops` at most 3). *Matching*: the `Location` is resolved against the request URL; scheme, host and port must equal the admitted origin (userinfo, fragment and an https-to-http change are refused); the path is compared **byte-exact** with the hop's `pathTemplate`, each `PATH_SEGMENT` slot occupying exactly one segment whose bytes satisfy the slot's closed `shape` (UUID, UINT, HEX or ENUM) and are a member of the slot's plan-known `values[]` — which excludes `%`, `;`, backslash, `/`, dot-only segments, whitespace, control bytes and non-ASCII, so encoded or double-encoded forms never match; the query must be **exactly** the hop's `queryTemplate`: the same parameter names in the same order, each exactly once, no extra, repeated, reordered, empty-named or unlisted parameter and no fragment, each substituted value being the bytes of a `HOP_MATCHED` slot of a closed shape (query values are compared byte-exact and never decoded, so `%`, `+`, `;`, `&`, `=`, `#`, whitespace, control bytes and non-ASCII cannot occur in a substituted value); a `Location` that does not match is **not followed** and is recorded as the observation `redirect_not_followed` with a closed detail (`NO_PLANNED_TARGET`, `ENCODED_OR_AMBIGUOUS_PATH`, `CROSS_ORIGIN`, `SHAPE_MISMATCH`, `METHOD_NOT_PERMITTED`, `DEPTH`), and the check continues without it. `301/302/303` force `GET`; `307/308` are followed only when the planned target has the same method and classification. *Operation identity*: every `REDIRECT_HOP` step (and every step with a path-position slot) carries `operationRef`; at render time the parent requires an `OPERATION_DECLARATION` manifest item whose `operationKey` equals the step's resolved `METHOD /template` and whose `declaredClass` is `READ_ONLY` with `unsafeMethodAcknowledged` false (a hop is never `FIXTURE_CONFINED`, never a mutation, never an undeclared operation: an operation without a declaration is potentially mutating, FR-192/FR-007, so the hop is not planned). A hostile `Location` therefore selects only the values of closed-shape identifiers (path and query) inside a template that was planned and that the customer declared read-only; it cannot select a different path or query parameter such as a logout, delete or reset endpoint (the template's literal segments and parameter names are fixed, the shapes cannot spell a word, and an `ENUM` list is fixed in the plan). **`READ_ONLY` is a customer assertion (L3)**: `declaredClass` is what the customer declared and is reported as customer-asserted (FR-192); 012 does not and cannot prove that the endpoint is non-mutating. The controls are the planned template, closed typed values, the state-changing-word list, classification at most `C1`, method `GET` or `HEAD`, the same identity and origin, at most 3 hops, full re-admission and the optional `protectedMarkerRef` tripwire (a missing marker is reported as unverified); a customer who misdeclares a mutating operation as `READ_ONLY` and plans it as a hop carries that residual risk, and the evidence labels the hop `customer-asserted`. As defence in depth the registry carries a closed list of state-changing words (`logout`, `signout`, `delete`, `remove`, `revoke`, `reset`, `unsubscribe`, `activate`, `cancel`, `disable`, `confirm`): a hop template with such a literal segment, or an `ENUM` value equal to one, is refused when the table is rendered. *Identity and provenance*: the hop executes with the originating step's identity and credential slot values only; the `Location` bytes are read from the `ResponseRecord` of that identity, destination and attempt (a record of another identity, destination or attempt, a truncated or stale record, or one already consumed makes the hop not followed). *Re-admission*: a followed hop is a fresh admission of the target step: destination, rendered path bytes (which must equal the `Location` path), method, identity, consent (FR-177), `ActiveTestingEnablement`, scope (`securityScopeGate` on the raw form; the single-decoded form is identical because no `%` can occur), action category, mutation classification and the declared operation are re-derived from the step and re-validated after substitution (FR-190); it consumes its own F07 request unit and local budget; credential-class headers are stripped on any non-identical origin (FR-081) although only same-origin hops can match. A redirect can therefore never introduce an unplanned, undeclared or cross-identity request, nor a request to an operation the customer declared mutating or left undeclared; it cannot detect an operation the customer misdeclared as `READ_ONLY` (stated residual). (f) *Order and replay*: per-unit step state is held by the parent; a frame whose step is not an allowed successor of the last executed step, exceeds `maxExecutions`, names a step of another unit, identity or Target, or arrives while the previous admission is unresolved is refused; with `maxAttempts` 1 and the `sec-probe-attempt` claim the same step is not re-sent across attempts. (g) *Byte identity*: the bytes that were authorized are the bytes sent (FR-199). (h) *Compromised-child tests*: other-host or other-path step, different identity or category, extra field, out-of-order step, step replay beyond `maxExecutions`, child-supplied `RESPONSE_DERIVED` or `FIXTURE_IDENTIFIER` or `CANARY` value, a `CREDENTIAL` value outside the registry, substituted path, arbitrary or cross-origin redirect, redirect to an unplanned state-changing target, a hostile `Location` that names a logout or other credentialed endpoint, encoded, double-encoded, `;`, backslash, `//` or non-ASCII path confusion in a `Location`, a `Location` value substituted from another identity's response, a hop whose operation is undeclared or not `READ_ONLY`, a free-`TEXT` path or hop-query slot, a `Location` carrying an identifier outside the plan-known list, a `RESPONSE_DERIVED` value in a path position or used as an object identifier, a hostile `Location` query string (an extra, repeated, reordered, encoded, over-long or non-shape parameter or value, a fragment), a customer-misdeclared `READ_ONLY` operation (residual documented, evidence labelled customer-asserted), a child frame carrying a `HOP_MATCHED` value, 307/308 method preservation to an unplanned target, stale or truncated or cross-identity or cross-destination response provenance, an input item swapped, stale or mutated before parsing, a renderer read outside the manifest, and a restart that renders a different table are each refused with zero bytes on the wire (`SEC_EGRESS_PERMIT_INVALID`, detail `STEP_NOT_AUTHORIZED`, `SLOT_INVALID` or `PROVENANCE_UNAVAILABLE`; the redirect cases are the non-followed observation above; `SEC_SCOPE_GATE_ERROR` for input mismatches and invalid tables) and an audit event. **Stated residual**: a compromised child can still choose among the steps the plan authorized, in the allowed order, and use its own session secrets; it cannot create a request the plan did not authorize or steer one with values it authored.
- **FR-201** (database privilege isolation, authenticated principals and durable broker state — F-02, A3, A4, N5-3 to N5-8; mandatory activation prerequisite, AR-13 REQUIRED FOR ACTIVATION): the broker's protection against a compromised worker depends on enforceable database permissions; MAC validation alone is not the trust boundary. Broker issuance and every active/authenticated engine stay disabled (SG3, SG10) until a deployed, tested privilege boundary exists, or a technically equivalent alternative has been explicitly approved after an independent review. (a) *Roles and positive grants*: `fahes_worker_exec` (a NOLOGIN provisioning template: its grants are copied to each instance's own NOINHERIT login role by the provisioning step, with no runtime role inheritance, data-model 4.10E; each worker instance connects with its own login role registered in `WorkerPrincipal`, so `session_user` identifies the instance), `fahes_orchestrator` (009's orchestrator, sweep, deadline and terminal-refund code), `fahes_api_planner`, `fahes_broker`, `fahes_operator` and `fahes_sec_derive` (the evaluator and finalizer service that writes parent-derived records, data-model 4.10D). The grants are **positive**: each role has only the privileges in the matrix of `data-model.md` section 4.10A, and every table not listed is denied (REVOKE ALL). In particular, for units of the 012 classes `fahes_worker_exec` has **no direct INSERT, UPDATE, DELETE or SELECT** on any protected table: it holds EXECUTE only on the claim-scoped functions of clause (j) and 4.10D (`sec_peek_unit`, `sec_claim_unit_host`, `sec_record_step_table`, `sec_unit_context`, `sec_read_input`, `sec_transition_unit`, `sec_finalize_unit`, `sec_refuse_unclaimed_unit`, the `sec_f07_*` wrappers of 4.10C, `sec_append_evidence`, `sec_register_artifact`, `sec_read_evidence`, `sec_probe_*`, `sec_mutation_*`, `sec_report_progress`, `sec_stop_pending`), and **no access** to the vault, `AuthAttemptReservation`, `BrokerPrincipalState`, `BrokerPrincipalIssueEvent`, `UnitDispatchRecord`, `WorkerPrincipal` or `SecuritySettlement`. (b) *Authenticated principals*: the functions and the broker never trust a caller-asserted `principalId` or `hostInstanceId`: the database functions derive the principal from `session_user` joined to `WorkerPrincipal(loginRole, principalId, registeredAt, revokedAt, registeredBy)` (operator-provisioned; a revoked or unregistered login is refused), and the broker derives it from the mTLS/workload identity of the connection (the same registry). A principal exists only through the operator-only security-definer function `sec_register_worker_principal(principalId, loginRole, mtlsSubject, servedClasses, servedTenantIds)`, which inserts the `WorkerPrincipal` row and its `BrokerPrincipalState` row (zero breach counters, not quarantined) in one transaction; `sec_revoke_worker_principal` sets `revokedAt`; no role has direct INSERT/UPDATE on either table, and the broker and `sec_claim_unit_host` refuse a principal that has no `BrokerPrincipalState` row (fail closed, a registration error, not an anomaly). `servedClasses` is a non-empty subset of `{ACTIVE_SECURITY, AUTHENTICATED_WORKFLOW}`; `servedTenantIds` is empty for a shared pool (any tenant) or a non-empty list that makes `sec_claim_unit_host` refuse every other tenant's unit (Mode S, OD-4). (c) *Transition and finalization functions (aligned with 009)*: no function creates or reinterprets an `ExecutionUnitStatus`; each only guards an edge that 009 already has. `sec_claim_unit_host(unitId, attempt)` changes no status. It evaluates, in this fixed order: (1) the session principal is registered, unrevoked and has its `BrokerPrincipalState` row; (2) the principal is not quarantined; (3) the unit exists, is an active/authenticated unit that is neither terminal nor `RUNNING`, **and its `executionUnitClass` is in `servedClasses`**; (4) the unit's tenant, read from the unit row, is in `servedTenantIds` when that list is non-empty; (5) the plan and scan are live before `effectiveDeadlineAt` (database clock); then, under the principal-row lock, (6) rule CS1 of FR-173 and (7) no existing `UnitDispatchRecord` for `(unitId, attempt)`. Failures of steps 1 to 5 return one uniform denial that is identical to a nonexistent unit (clause (l)); a CS1 denial concerns only the caller's own behavior. Only then it inserts the `UnitDispatchRecord` (`dispatchSeq` from a database sequence, `dispatchedAt`, `principalId` from the session, `hostInstanceId` = the principal) and the `sec-unit-host` claim atomically. `sec_record_step_table(unitId, attempt, tableDigest, inputsRootDigest)` records the digest once for the claim owner. `sec_transition_unit(unitId, attempt, from, to)` is the guarded CAS `transitionStatus` for the **three non-terminal edges only** — `PLANNED->ADMITTED`, `ADMITTED->DISPATCHED`, `DISPATCHED->RUNNING` — and only for the claim owner; it never writes a terminal status (a terminal request is `TransitionRejected`). `PLANNED->ADMITTED` additionally requires a live F07 `AdmissionLease` for the unit (unreleased, unexpired on the database clock, grant id among the unit's `grantIds`) as evidence that the dispatch checkpoint returned `PROCEED`; that lease is a liveness fence, not authority (a compromised worker can write leases through 008's functions; the per-request checkpoint remains the authority). The edges come from `ExecutionUnitTransitionPolicy`, a function constant generated from the 009 implementation and compared with it at activation (SG1); if an edge 012 needs is absent from that table, activation is blocked and the amendment is raised (AR-18); 012 never adds an edge. **There is exactly one internal terminal-status body, `sec_finalize_body`, with three narrow entry points; no other code path and no caller-chosen target status reaches a terminal status (7th-pass F3).** The body executes 009's `finalizeExecutionUnit` semantics in one database transaction: (1) idempotency on `(unitId, idempotencyKey)` (an identical retry returns the prior outcome; a different outcome or reason for a terminal unit is refused and changes nothing); (2) the entry point's authority check below, evaluated after taking the `ExecutionUnit` row `FOR UPDATE` (the lock `sec_claim_unit_host` also takes, so claim and finalize serialize and exactly one wins); (3) release of the unit's F07 `AdmissionLease` through the transactional 008 release capability of data-model 4.10C (a lease already released, expired or reclaimed is an idempotent no-op, never a failure); (4) the guarded status write using the 009 edge for the status read under the lock (`REFUSED` from `PLANNED`, `ADMITTED` or `DISPATCHED`; `COMPLETED`, `FAILED`, `CANCELLED`, `KILLED` only from `RUNNING`; any other pair is `TransitionRejected` and rolls everything back); (5) one-level `BLOCKED` propagation, only for outcomes other than `COMPLETED`, only to `ExecutionDependency` rows whose `dependsOnExecutionUnitId` is this unit and whose dependent has the same `scanPlanId` and `userId` and is still `PLANNED` (no other unit, plan or tenant is reachable); (6) the final `progressSnapshot`; (7) an `AuditLogEntry` `unit.finalize` recording the entry point, the authenticated principal, the reason and `reasonVerified`. A failure at any step rolls back the whole transaction, so there is never a half-finalized unit (lease released but status unchanged, or the reverse); a retry with the same idempotency key is safe. **Entry points:** (i) `sec_finalize_unit(unitId, attempt, outcome)` is **for the claim owner only**: it requires the `UnitDispatchRecord` of `(unitId, attempt)` whose `principalId` equals the session principal (derived from `session_user`, never an argument), the matching `sec-unit-host` claim and the unit's class in the principal's `servedClasses`; no claim, another principal's claim or a stale attempt is denied. `outcome` is a closed union checked against the status held: a `REFUSED` outcome carries a `reasonCode` from the closed matrix of data-model 4.10B (never free text), every reason that has a database predicate is verified and a false predicate is denied (`FinalizeDenied(REASON_NOT_VERIFIED)`), host-asserted reasons are recorded `reasonVerified=false`; `COMPLETED`, `FAILED`, `CANCELLED` and `KILLED` are accepted only from `RUNNING`, with `failureClass` and F07 reasons from the closed 009 sets. (ii) `sec_refuse_unclaimed_unit(unitId, reasonCode)` is **the only path without a claim and is deliberately narrow**: it can only produce `REFUSED` (the caller supplies no status or outcome); the caller must be a registered, unrevoked principal; the unit must be of class `ACTIVE_SECURITY` or `AUTHENTICATED_WORKFLOW` and in the caller's `servedClasses`, and its tenant, read from the unit row, must be in `servedTenantIds` when that list is non-empty (a failure is the uniform denial of clause (l)); the status read under the row lock must be `PLANNED`, with no `UnitDispatchRecord` and no unreleased `AdmissionLease` for the unit; `reasonCode` must be one of the four tier-U reasons of 4.10B (`SCAN_CANCELLED`, `SCAN_FAILED`, `SCAN_DEADLINE_EXPIRED`, `SCAN_DEADLINE_INSUFFICIENT`: 009 dispatch step 0 only) **and its database predicate must be true on the database clock**; tenant, plan, scan, deadline and the unit's timing are read from the unit's own rows, never supplied. Anything else (an unverifiable reason, another status, a class outside `servedClasses`, a tenant outside a non-empty `servedTenantIds`, an existing claim) is denied (`FinalizeDenied`, audit `unit.finalize_denied` with principal, unit and reason): the host stops without finalizing and the unit stays `PLANNED` until a host claims it or the orchestrator sweep ends it; a denial never degrades into a caller-controlled refusal, so a feature-flag, environment, checkpoint, proof or input refusal, none of which has a worker-unforgeable predicate for an unclaimed unit, is made **after** `sec_claim_unit_host` as the claim owner. (iii) `sec_sweep_finalize_unit(unitId, terminationConfirmed)` is callable only by the `fahes_orchestrator` login (no `EXECUTE` for any worker role, a test fails the build otherwise) and takes **no outcome and no reason from its caller**: the function derives the cause from database state (scan state, `effectiveDeadlineAt`, `KillSwitchState`) and applies exactly the cell of 009's status-by-cause matrix (`scan-deadline-contract.md`) for the status held; if no cause applies it denies (`NO_CAUSE`); a `RUNNING` unit is finalized only when `terminationConfirmed` is true (the engine's `onUnitExpired` returned `TERMINATED`) or, past `hardStopMarginMs` after the deadline, as `FAILED`/`TERMINATION_UNCONFIRMED`; every table a cause predicate reads (`Scan`, `ScanPlan`, `KillSwitchState`, `Target`/`TargetAuthorization`, `ExecutionUnit` timing columns) is one on which no worker role has write privilege (test `db.refusal-predicate-tables-not-worker-writable`), so a compromised worker can neither call the sweep nor create the cause it reads. A host that crashed before finalizing keeps its claim (never stale-reclaimed) and the orchestrator finishes the unit through the sweep. If 008's release capability cannot run inside the finalizing transaction (data-model 4.10C), activation (SG1) is blocked and the gap is raised through AR-13/AR-18; 012 does not release a lease outside the transaction. (d) *Transition ownership (every edge named)*: `PLANNED->ADMITTED`, `ADMITTED->DISPATCHED` and `DISPATCHED->RUNNING` are owned by the claim-owning host through `sec_transition_unit`; `PLANNED|ADMITTED|DISPATCHED -> REFUSED` (every pre-run refusal; `KILLED` does not exist before `RUNNING`) by the claim-owning host through `sec_finalize_unit` or, for `PLANNED` units with no claim and only the four database-verified tier-U reasons, by a registered principal serving the class through `sec_refuse_unclaimed_unit`, or by the orchestrator sweep; `RUNNING -> COMPLETED|FAILED|CANCELLED|KILLED` by the host (`sec_finalize_unit`) or, after the SIGKILL deadline and the termination-confirmation rule, by the orchestrator sweep (`sec_sweep_finalize_unit`); `PLANNED -> SKIPPED` is written by plan resolution (`fahes_api_planner`) and `-> BLOCKED` only inside a finalize (step 5); the worker role writes no status column directly. 012 adds no edge and no status. (e) *Retry, crash and fencing*: `retryPolicy.maxAttempts` is 1 (FR-057); a crashed host keeps its claim (never stale-reclaimed); the unit is finished by the orchestrator sweep; a second host's `sec_claim_unit_host` conflicts and it must not transition or finalize. (f) *Broker verification* (its own role; every worker-callable broker operation, not only issue: `reserveAuthAttempt`, `markAuthAttemptSent`, `resolveAuthAttempt`, `releaseAuthAttempt`, `getLeaseStatus`, `confirmLeaseDestroyed`, MA-01): for issue, the unit is `RUNNING` with a `UnitDispatchRecord` whose `principalId` equals the authenticated principal, `dispatchedAt` inside the lease window and a `dispatchSeq` not seen before, scan and plan non-terminal and before deadline, and `(unitId, attempt)` has no earlier lease: a historical, terminal, already-leased or other-principal unit is denied. For the other six operations the same `UnitDispatchRecord` principal equality, the identity's membership in the unit's verified credential binding and the existence of the lease or reservation row are required, and a failure is an integrity denial that changes no state (credential-broker consolidated item 12). (g) *Durable shared anomaly state*: `BrokerPrincipalIssueEvent` and `BrokerPrincipalState` (quarantine) are rows read and written under the lock order of FR-173, never broker memory; a restart or a second replica neither resets nor fragments a window or a quarantine. (h) *Migration*: roles, grants and functions (including `sec_register_worker_principal`, `sec_revoke_worker_principal` and the `vault_*` owner and operator functions of data-model 4.10A) are migration M012-7; the tables are in M012-5e. The REVOKEs on 007/008/009-owned tables need those specs' implementation owners (AR-13, cross-owner scheduling is an owner decision) but change no frozen document text. (i) *Acceptance evidence for SG3/SG10*: a privilege-bypass suite (each denied write attempted as `fahes_worker_exec` fails; a forged status flip, forged claim, kill-switch delete and direct `UnitDispatchRecord` write are denied; a caller-asserted `principalId`/`hostInstanceId` argument is rejected), a replayed-historical-unit test, a transition-policy equality test against the 009 implementation, a finalize-atomicity suite (lease release, `BLOCKED` propagation, snapshot and audit commit or roll back together; idempotent retry; claim race), an unclaimed-refusal and sweep-abuse suite (wrong class, cross-tenant, forged reason, missing claim, expired lease, claim versus finalize race, replay after finalization, dependency-propagation abuse, compromised worker principal, sweep not callable by a worker; T822, T829), a class-scoping test (a unit of a class outside `servedClasses` cannot be claimed), and concurrency tests (two broker replicas racing issues for one principal and for one tenant stay within R1-R7; a replica restart keeps windows and quarantine; lock-order deadlock retry never grants), the write and read confinement suite of clause (j) (T852 to T863), and the SPEC 008 integration suite of 4.10C (T835, T860). (j) *Claim-scoped write and read confinement (MA-07, MA-17, MA-18; data-model 4.10A, 4.10C, 4.10D)*: for units of `ACTIVE_SECURITY` and `AUTHENTICATED_WORKFLOW`, a worker role has no direct DML or SELECT on `Evidence`, `Artifact`, `Issue`, `IssueEvidenceLink`, `ModuleResult`, `CapabilityExecution`, `MutationIntent`, the `sec-*` `IdempotentClaim` scopes, `ExecutionUnit.progressSnapshot`, the 012 tenant tables, another tenant's `ExecutionUnit`, `ScanPlan`, `Scan`, `TargetAuthorization`, `ScopeDefinition` rows, `KillSwitchState`, `AdmissionLease` or `BudgetConsumption`; every worker read and write is a security-definer function that first derives its context (`sec_ctx`: the authenticated principal, its non-revoked and non-quarantined `WorkerPrincipal`, the live `UnitDispatchRecord` of `(unitId, attempt)` owned by that principal, the unit's class in `servedClasses`, tenant, plan, target and grants read from the unit and plan rows, an allowed unit status, plan and scan non-terminal and before the database-clock deadline, no pending kill switch, a live `AdmissionLease` where the function consumes budget) and takes **no argument that names a tenant, scan, plan, target, grant, status or record owner**; every identifier it does accept (check, step, fixture, identity, manifest item) must be a member of the unit's MAC-covered configuration or manifest; the record kinds and edges each function accepts are closed. Parent-derived records (`SECURITY_CHECK_RESULT`, `API_SURFACE`, `ADVISORY_MATCH`, residual manifests, `Issue`, `IssueEvidenceLink`, `ModuleResult(SECURITY)`, `sec-check-execution` claims, reverify state) are written only by `fahes_sec_derive` through `sec_derive_*` functions that derive tenant and plan from the `ScanPlan` row and require every producing unit terminal; the worker-side `onSecurityEvidenceCommitted` hook only enqueues ids. A database trigger denies any worker role an `UPDATE` of `ModuleResult(SECURITY)` once `coverageComplete` is non-null. The 008 admission, checkpoint and release operations are reached only through the claim-bound wrappers of 4.10C (MA-18). The claim itself is not tenant-scoped unless the principal is registered with `servedTenantIds`: tenant isolation under worker compromise is therefore claimed **only** for principals registered with `servedTenantIds` and routed to those tenants' jobs (Mode S; owner decision OD-4; AR-20); under a shared pool the reachable tenant set is bounded by rule CS1 (FR-173) and not eliminated. Units of other execution classes and the legacy SECURITY capabilities are not confined by this clause (AR-21). (k) *Privileged-function hardening (IC-1; data-model 4.10E)*: every `sec_*`, `vault_*` and `sec_derive_*` function, the 4.10C wrappers and the `f07_*` internals are created and operated under the twelve requirements of 4.10E: a fixed, trusted `search_path` that no worker, API, operator or evaluator login can create objects in (`pg_temp` last, no TEMP privilege for workers); schema-qualified references; `REVOKE EXECUTE ... FROM PUBLIC` and a minimal role-specific `GRANT EXECUTE` that matches 4.10A exactly; function owners that are dedicated NOLOGIN, non-superuser, NOBYPASSRLS roles holding only their family's table privileges; NOINHERIT worker instance logins with no membership that reaches an owner role and no `SET ROLE`; no unsafe dynamic SQL; strict argument validation before any read; exceptions mapped to closed codes that carry no row data; no role in the matrix holds CREATE or TEMP, by explicit REVOKE from PUBLIC and from each role verified on effective privilege (F5, data-model 4.10E.1). The boundary of clauses (c), (j), (l) and (m) is not in force until the hardening suite (T865, T866) is green in the target deployment; SG3 and SG10 require it. (l) *Pre-claim boundary and Mode S (IC-2; data-model 4.10D)*: every function a principal can call before it holds a claim (`sec_peek_unit`, `sec_claim_unit_host`, `sec_refuse_unclaimed_unit`) derives the unit's tenant from the unit row, never from an argument, and applies, before it reveals or changes anything, the registered, unrevoked, non-quarantined principal check, the `servedClasses` check and, when `servedTenantIds` is non-empty, the tenant check. For a unit outside the principal's classes or tenants, or one that does not exist, the response is one fixed **returned** structured result (not an exception, SQLSTATE success) with the same shape and code for every cause (no existence, status, scan, deadline, class or tenant oracle; the same lookup work is performed so latency does not distinguish the cases), nothing is mutated, no F07 budget, lease or kill-switch state is touched (the 008 wrappers require a claim), and the denial is audited in the same database transaction (no autonomous transaction, dblink or other shortcut) at platform scope only: `AuditLogEntry` with `actorId` and `subjectId` the platform-assigned principal id, `subjectType` `WORKER_PRINCIPAL`, and a closed `after` that holds no unit id, hash of it, tenant, scan or plan id, never in any tenant-visible audit log or response. Emission is bounded by durable per-principal counters in the database (first A denials per 10-minute window audited, the rest only counted, one summary row per window, never Redis), and a count of Q in a window quarantines the principal with reason `PRE_CLAIM_PROBING` (F2, F3; data-model 4.10D). A caller that rolls back its own transaction erases its own audit row and learns nothing from it (named limit). In a shared pool (empty `servedTenantIds`) these functions are tenant-agnostic by design; the boundary applies only in Mode S. (m) *Principal identity under connection pooling (F6; data-model 4.10E.2)*: the worker principal is derived only from `session_user` of the executing server connection and never from an argument, `application_name`, a GUC or a forwarded header; direct connections and session pooling are supported, transaction pooling only with per-login pools verified through the real path, and a shared-credential proxy is not supported; if the principal cannot be established every function denies (fail closed), and the conformance probe `sec_principal_probe` and the T881 suite are an activation condition.

## Success Criteria *(mandatory)*

- **SC-001**: In a fixture suite of ≥ 40 deterministic scenarios (plan.md §"Testing the tester"), 100 % of safety invariants hold: zero requests without checkpoint, zero raw secrets in any persisted/queue/log/AI surface, zero PASS for non-executed checks.
- **SC-002**: For every `FAILED/REFUSED/BLOCKED/NOT_TESTED/UNSUPPORTED/INCONCLUSIVE` check the report names a closed `SEC_*` or upstream reason; the number of "free text" reasons is zero.
- **SC-003**: A scan whose active units were all refused yields a SECURITY result of `DEGRADED` (with `coverageComplete: false` and the coverage summary attached) or `NOT_APPLICABLE` (null score) in 100 % of fixture runs; it never yields a `COMPLETE` result.
- **SC-004**: After any termination path (complete, fail, cancel, kill, deadline, crash), broker leases are `REVOKED/DESTROYED` and no session jar exists within `hardStopMarginMs`; residual server-side sessions/mutations are listed explicitly.
- **SC-005**: Adversarial review: all 50 required scenarios plus 28 additional (adversarial-review.md) each have a named preventive mechanism, owning contract and acceptance test, with residual limitations stated; every WEAK/GAP rating has a disposition (§Disposition in that file) that is either a repair landed in this package (FR-172..FR-187 and contract addenda) or a recorded residual risk.
- **SC-006**: No frozen upstream document is modified; every upstream gap is in `upstream-amendment-requests.md`.
